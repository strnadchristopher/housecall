# Shared client engineering

React + TypeScript runs in the browser and Tauri 2 shell. `src/ui/` remains untouched after the initial milestone: Opus owns presentation, interactions, themes and motion. `App.tsx` adapts server data and intents to the unstyled `Screen` contract; `hooks/`, `state/`, `transport/`, and `data/` own implementation. No visual styles or third-party trackers are included.

Run `cd client && npm ci && npm run dev`; Vite proxies `/api` to `HOUSECALL_API` (default `http://127.0.0.1:3000`). `npm run build` typechecks and outputs `dist/`. Production serves that directory beside the API. A packaged native client takes a server URL on the authentication form; only HTTPS is accepted except loopback development. `VITE_API_ORIGIN` supplies an optional build-time default, never a secret. The API must explicitly allow the native app origin. Invite links contain the single-use invite token in the fragment, so the HTTP server and referrer do not receive it. Accepted tokens are removed from browser history.

WebView authentication sessions and device secrets live only in memory; reload requires sign-in. An explicit Android background-push opt-in separately grants the native worker Keystore-encrypted, backup-excluded storage; see NATIVE-PUSH.md. They never enter URLs, persistent browser storage, logs, or presentation props. The native background grant is cleared before account replacement, sign-out or current-device revocation; it is never returned to the WebView. Logout revokes the current server session. Device UI can revoke another session. Browser fetch omits cookies, disallows redirects, and disables cache. The Tauri shell exposes no filesystem, shell execution, or remote IPC plugin permissions.

The currently wired slice includes WebAuthn registration and sign-in, first-run setup, invite redemption, password sign-in, owner invite issuance, chunked upload/pause/resume/quarantine and attachment selection, conversation listing, messages, edits with revision, replies, user mention completion, reactions, pins, search, DMs/group DMs, consented text reports, report resolution, device revocation, and one-second durable event polling. Server events trigger authorized refetches. Unsend installs a permanent in-memory tombstone and closes matching browser notification handles. Tombstones beat late responses and out-of-order edits. No cached message is displayed across a reload. This is actual browser notification closure while the process runs, not a claim of background APNs/FCM delivery or offline operating-system alert erasure.

Android secure background-push storage and reconciliation now have an implementation candidate, with compilation/device gates recorded in NATIVE-PUSH.md. Dedicated thread views, formatted markdown presentation, integrated VM playback, themes and native invite deep links remain incomplete. DJ/Plex playback and consented screenshot reporting have local fixture evidence in PROGRESS.md; live provider/device acceptance remains separate. Browser voice includes microphone/camera, screen replacement, incoming tracks, target stereo/fullband 510 kbps, optional noise suppression, mute, and counters; actual SFU interoperability is verified below, while physical latency remains unmeasured. Plex provider integration is being verified separately; unavailable activity providers remain explicitly labeled. Gimme exposes dry-run preview only. Giphy results retain attribution and select a link into the composer when a server key is present. The contract inventory is broader than this completed slice. No placeholder is acceptance evidence.

## Tests and evidence

`npm test` covers stale response resurrection after unsend, revision ordering, channel isolation, notification closure and ordering, insecure origin rejection, and precise mention matching. `npm run e2e` launches the compiled `target/debug/housecall-server` in an isolated temporary database with loopback API port 3031 and frontend port 1420. It sets a fixture bootstrap token and media key, removes its own directory on exit, and never wipes existing user databases. The test opens three isolated browser contexts against the real API and covers setup/invites, realtime messages, mentions, browser notification closure after unsend, edits, replies, pins, search, private DM isolation and session revocation. It also validates WebAuthn using a Chromium virtual authenticator, rejects registration/assertion replay, checks the old bearer after revocation, synchronizes all three activity control types, previews Gimme without provider mutation, and tests fail-closed quarantine after a 5 MiB upload. It uses a deterministic Notification adapter to observe OS notification calls without desktop permissions, not an API mock. JSON results and a screenshot are written under `evidence/client-*`. Playwright tracing and automatic failure screenshots are disabled to avoid recording auth headers or request credentials. The manual success screenshot contains only fixture conversation data.

## Contract changes for root handoff

Append to UI-CONTRACT changelog: login/setup/invite fields include optional `server_origin`; device secret storage is currently memory-only. Generic field types add `file` for functional upload selection. Voice stream binding lives in the engineering MediaTrack adapter, using an unstyled browser media element, with no custom visuals. Generic composer receives mention-candidate items with `mention` intent and `itemId=user.id`; engineering collects draft input and throttles typing transport. Message item actions are reply/react/pin/edit/unsend. Search/pins reuse current channel; all list/query content filters durable deletion tombstones. Native/background capabilities remain unavailable and are not advertised as shipped.

## Additional verified client transport work

The three-browser SFU test now passes against the actual Rust server: each browser receives two Opus audio streams with packets and decodes two VP8 video streams. See `evidence/client-voice-three-user.json` and `evidence/client-voice-e2e.txt`. Capture devices are Chromium's synthetic devices. This proves transport/decoding, not physical camera-to-display latency, achieved 510 kbps audio, native media permissions, or 30-user capacity. Screen sharing replaces the camera track and preserves microphone audio; simultaneous camera/screen and system audio remain unimplemented.

Explicit link preview requests render sanitized text from the server. Markdown is parsed into inert semantic nodes (`data/markdown.ts`); HTML and images never execute/fetch in this layer. The Opus presentation layer still needs to consume those nodes to render formatted markdown. Roles support multiword names, longest-name matching, and autocomplete; generic server/channel/role administration uses the existing Screen contract.

`tests/e2e/voice-load.spec.ts` provisions 30 separate browser contexts, then ramps real SFU media through 5/10/20/30 peers. Run `HOUSECALL_TEST_LOAD=1 npm run test:voice` after builds finish. It uses 320×180 at 5 fps, default 510000-bit Opus target, a 60-second media phase, a 6 GiB summed Chromium/SFU RSS guard and a 1.5 GiB available-memory guard. Results go to `evidence/client-voice-load.json`; a harness existing is not a passing load result. CPU samples use process lifetime averages and summed RSS can count shared pages twice.

Plex HLS uses hls.js FetchLoader with authenticated requests restricted to the configured API origin, credentials omitted, and redirects rejected. Provider credentials never enter URLs or browser state. MediaSource support is required; browsers without it report an explicit limitation. Native HLS cannot attach bearer/device headers and is intentionally not used as an insecure fallback. The media binding follows authoritative activity timestamps, adjusts drift above 350 ms, and handles play/pause and available HLS subtitles. Provider/browser integration evidence is still pending.
