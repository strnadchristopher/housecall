# Housecall protocol specification, version 1

Status: draft for implementation. No independent audit has happened. Read `THREAT-MODEL.md` for what this protocol does and does not protect, `SECURITY-LEVELS.md` for the labels members see, `DECISIONS.md` for why it looks like this, and `CRACK-PLAN.md` for how it will be attacked.

Words "must", "must not" and "should" are used in the RFC 2119 sense. "Client" means a Housecall app (Tauri desktop or mobile, or the web client). "Server" means the `housecall-server` process and everything the host operator controls on that machine. "Host" means the person or party operating the server. "Owner" is the first account that set the server up.

## 0. Conventions

### 0.1 Encoding

- All structured data is CBOR (RFC 8949) with deterministic encoding (section 4.2.1 of the RFC): definite lengths, shortest integer forms, map keys sorted bytewise. Maps use small integers as keys. Field tables below are written `key name: type`.
- **Signed objects are byte strings.** A signed object is `{payload: bstr, sig: bstr(64)}`. The signature covers the exact `payload` bytes as transmitted. A verifier must verify the signature over the received bytes first and only then parse `payload`. It must never re-encode and then verify.
- A parser must reject: duplicate map keys, indefinite lengths, non-shortest integers, trailing bytes, unknown map keys inside signed objects of a known version, and any object whose `v` is higher than the client implements (fail closed, show "update required").
- Time is milliseconds since the Unix epoch. No security decision depends on a wall clock except the TTLs in 0.4, and those tolerate 5 minutes of skew.
- Lengths: `bstr32` means exactly 32 bytes.

### 0.2 Domain separation

Every hash, signature, KDF call and AEAD associated-data string starts with a label from the list in 0.6. Labels are ASCII, start with `hc/v1/`, and are never reused for two purposes.

- `H(label, p1, p2, …)` = SHA-256( u8(len(label)) ‖ label ‖ for each part: u32be(len(p)) ‖ p ).
- `Sign(sk, label, payload)` = Ed25519 over ( u8(len(label)) ‖ label ‖ payload ). Plain Ed25519 (RFC 8032), not Ed25519ph.
- `Verify` must use strict verification (reject non-canonical `S` and small-order points).
- `KDF(ikm, salt, label, parts…, L)` = HKDF-SHA256 (RFC 5869) with `info` = u8(len(label)) ‖ label ‖ for each part: u32be(len(p)) ‖ p.
- `AEAD` means XChaCha20-Poly1305 (24-byte random nonce, 16-byte tag) unless a section says otherwise. The nonce is generated by the sender with the OS CSPRNG and sent with the ciphertext.

## 1. Keys and identifiers

### 1.1 Account root secret

`RS` is 32 random bytes generated once on the device that creates the account (CSPRNG). It is the account. Whoever holds `RS` is the account for every purpose in this protocol. `RS` is never sent to any server in the clear. It leaves a device only as (a) the password-encrypted blob (2.3), (b) the recovery phrase (8.1).

Derived keys (HKDF-SHA256, `salt` = ASCII `hc/v1`, `L` = 32):

| Key | Derivation | Use |
|---|---|---|
| `ak_sign` | Ed25519 seed from `KDF(RS, label "ak-sign")` | Signs log entries, epoch headers, messages, device certificates, join requests, friend requests |
| `ak_dh` | X25519 secret from `KDF(RS, label "ak-dh")` | HPKE recipient key for channel-key wraps, friend requests, DM keys |
| `K_state` | `KDF(RS, label "state")` | AEAD key for the account's private synced state (7.5) |

`AccountPub` is the two public halves. Creating an account is entirely local: generate `RS`, derive, compute `account_id`. No server is involved.

### 1.2 Device keys

Each device generates, on first run:

- `DK`: an Ed25519 key pair for authenticating sessions. Stored in the platform secure store when one exists (Keychain, Android Keystore-wrapped file, DPAPI, Secret Service). A hardware-bound non-exportable key is not used because Secure Enclave and Android StrongBox do not support Ed25519 (see DECISIONS).
- `device_id`: 16 random bytes.
- `push_key`: an X25519 key pair used only for sealed push payloads (17.3).

`DeviceCert` is a signed object under `ak_sign`, label `hc/v1/devcert`:

```
payload { 1 v:1, 2 account_id:bstr32, 3 device_id:bstr16, 4 device_pub:bstr32,
          5 created_at:uint }
```

The certificate is not tied to one server, so one device registers it at every server it joins.

**What a device key is for.** Every device also holds `RS` (that is how it reads history). So `DK` gives per-device session authentication and per-device server-side revocation. It does not give cryptographic device revocation: a revoked device that was ever unlocked still knows `RS` (see Threat model, L5, and 8.4).

### 1.3 Storage of `RS` on a device

- Desktop and mobile: `RS` and `DK` live in the Rust process. The webview never receives them. At rest they are encrypted with a key held in the platform secure store. An optional app lock (OS biometric or passcode prompt) gates unwrap.
- Web: `RS` lives in a dedicated Worker running the crypto WASM. The main thread never holds `RS`; it sends the Worker requests and receives results. Default is session-only: the password is asked again in each new browser session. "Remember on this browser" stores `RS` encrypted by a non-extractable WebCrypto AES-GCM key in IndexedDB. This protects against copying the database, not against script running in the origin (it can ask the Worker for anything, and can use the non-extractable key).
- Secrets are zeroized when no longer needed (`zeroize`). Log lines never contain secrets, wrapped keys, or tokens.

## 2. Password, OPAQUE and the key blob

The password never reaches any server. The server learns nothing it can use to test password guesses without also holding its own OPAQUE secret (2.5).

### 2.1 Password and username rules

- The client NFKC-normalises the password, rejects it if shorter than 12 bytes, longer than 256, or zxcvbn score < 3, and does not trim whitespace.
- Usernames: see 0.4. A username is unique per server and chosen at account creation time on the device. The same username may belong to different accounts on different servers (13.6).

### 2.2 OPAQUE registration (per server)

Each server has its own OPAQUE `ServerSetup` (OPRF seed and AKE key pair). A registration therefore differs per server, so the OPAQUE records on two servers cannot be linked, and the export key differs per server.

Identifiers: client identity = username; server identity = hex(`server_id`). Binding the server identity means a record for server A cannot be replayed against server B.

Registration happens when a user asks to join a server (section 5). Messages (all inside the join request exchange, 5.3):

```
C→S  reg_start   { username, request: opaque RegistrationRequest }
S→C  reg_resp    { response: opaque RegistrationResponse }
C→S  reg_finish  { upload: opaque RegistrationUpload, blob: Blob }   (the finish message is carried in the join request)
```

The client obtains `export_key` (64 bytes) from `ClientRegistration::finish`.

### 2.3 The key blob

```
Blob { 1 v:1, 2 version:uint, 3 nonce:bstr24, 4 ct:bstr }
  key = KDF(export_key, salt="", label "blob", L=32)
  ct  = AEAD(key, nonce, plaintext, aad = H("hc/v1/blob", server_id, username, u32be(version)))
  plaintext = CBOR { 1 RS:bstr32, 2 account_pub:AccountPub, 3 created_at:uint }
```

The server stores `{username, opaque_record, blob, account_pub, version}`. `version` increases with each password change. After decrypting, the client must check that `account_pub` derived from the decrypted `RS` equals the `account_pub` that the signed log (3.3) lists for this username. If not, it aborts and shows "this server does not know you". This catches a server that serves another account's blob or a mismatched record.

**Honest limit.** `export_key` is a function of the password and the server's OPAQUE secret. Anyone who has the stored record, the blob, and the server's OPAQUE `ServerSetup` can test password guesses offline, each costing one Argon2id evaluation (m = 64 MiB, t = 3). A breached server with the OPAQUE setup therefore gets an offline attack on every user's password, and a guessed password yields `RS` for that account, which is the account on every server. Mitigations: the strength rule (2.1), the memory-hard parameters, and the at-rest wrap of `ServerSetup` under a key kept off the data volume (2.5). This limit is listed as L2 in the threat model.

### 2.4 OPAQUE login

```
C→S  login_start   { username, device_pub, request: opaque CredentialRequest }
S→C  login_resp    { response: opaque CredentialResponse, login_id }
C→S  login_finish  { login_id, finalization: opaque CredentialFinalization }
S→C  login_ok      { status: "granted" | "approval_required", pending_id? , blob? }
```

- Client login context (the `context` parameter of OPAQUE 3DH) = `"hc/v1/login" ‖ server_id ‖ device_pub`. The server verifies with the same context. A relayed login therefore cannot swap in a different device key.
- For an unknown username the server runs OPAQUE with a deterministic fake record derived from its seed and the username, so the response is indistinguishable and only the finish step fails. Timing of known and unknown names must not differ measurably.
- Client-side check: OPAQUE gives mutual authentication. If the server cannot complete the 3DH, the client aborts. A host that does not hold the record cannot pose as the server.
- On `granted` (no other active device, 7.2) the server returns the blob and the device continues with 7.3. On `approval_required` it returns a `pending_id` and a `pending` session token (6.3), and the blob only after approval (7.3).
- The OPAQUE session key from login is not used for anything else. Session authentication is section 6.

### 2.5 Server-side protection of OPAQUE secrets

The server has a 32-byte **at-rest wrap key `WK`**. It is created at install time and stored outside the data volume and outside backups (default: a root-owned `0400` file in a separate directory, `HOUSECALL_WRAP_KEY_FILE`; hardened mode: a passphrase entered at start, stretched with Argon2id at the host parameters in 0.4). The OPAQUE `ServerSetup` is stored AEAD-encrypted under a key derived from `WK`. A stolen data volume or backup alone therefore does not enable offline guessing against any password. A stolen whole machine image does, unless passphrase mode is used. If `WK` is lost, every password record is unusable; users with a device still signed in re-register (2.6), others use the recovery phrase (8.2) or admin re-approval (8.3). Backing up `WK` separately from the data is a documented operator duty.

### 2.6 Password change

Requires an authenticated device session **and** a fresh OPAQUE login of the old password (so an unlocked stolen device cannot silently change it).

1. Client logs in with the old password (2.4, context `"hc/v1/pwchange"`).
2. Client runs a new OPAQUE registration with the new password, builds a new `Blob` with `version + 1`, and sends `POST /v2/password` with `{upload, blob, sig}` where `sig` is `Sign(DK, "hc/v1/pwchange", H(upload, blob))`.
3. The server replaces the record and blob atomically and, if the request asks for it, revokes all other devices.
4. The client repeats this on every server the account has joined. Servers it cannot reach are queued and retried; until then the old password still works on those servers. The UI states this.

## 3. Server identity and the signed log

### 3.1 What the log is for

Without a signed membership list, a server can add a "ghost" member: a public key it controls, listed as a member, so that honest clients wrap channel keys to it. The log makes the member list something the server cannot forge. It also carries the host-assisted feature set (15), so the server cannot enable host access without the owner's signature.

The log is an append-only, hash-chained list of entries. Each entry is signed by the account that is allowed to make that change. Clients verify the whole chain from the genesis entry and recompute the state themselves. They never accept a membership or feature answer from the server that is not backed by the chain.

### 3.2 Entry format

```
LogEntry = SignedObject{ payload, sig }          signer = the account named in payload field 2
payload { 1 v:1,
          2 signer:account_id,
          3 server_id:bstr32,                    all zero in the genesis entry only
          4 seq:uint,                            genesis = 0, then +1
          5 prev:bstr32,                         entry_hash of the previous entry; all zero in genesis
          6 kind:uint,
          7 body:map,
          8 created_at:uint }                    advisory only
sig  = Sign(ak_sign of signer, "hc/v1/log-entry", payload)
entry_hash = H("hc/v1/log-entry", payload, sig)
server_id  = entry_hash of entry 0
```

The signer's public key is not inside the entry; the verifier looks it up from the state built so far (genesis names the owner's `AccountPub`; `member_add` and `member_join` entries carry the member's `AccountPub`).

### 3.3 Entry kinds and who may sign them

The verifier maintains a state: `members{account_id → {pub, username, display, role ∈ owner|admin|member|bot, joined_seq, history_mode, status}}`, `banned{ids, usernames}`, `channels{channel_id → {kind: public|private, creator, members, bots, archived}}`, `invites{invite_id → {issuer, used_by?, revoked}}`, `features`, `host_key`, `origin_hint`, `name`. An entry is valid only if every check in its row passes against the state **immediately before** it. An invalid entry makes the log invalid at that seq; the client stops, keeps the last valid prefix, and shows "Not verified" (SECURITY-LEVELS 7).

| # | Kind | Signer | Body | Extra checks |
|---|---|---|---|---|

**Invite expiry.** Expiry is policy enforced by the issuing server and by the issuing admin's device (revocation). It is not cryptographic because no trustworthy clock is available to every verifier. Single use *is* enforced by the chain: the first valid `member_join` for an `invite_id` wins; a second is invalid.

### 3.4 Publishing and ordering

- The server appends entries. Each submission names the `prev` it extends; the server accepts only if it equals its head (compare-and-swap) and the signature and rules check out, else it returns 409 and the client re-fetches and retries. The server runs the same validation as clients but clients never rely on it.
- `GET /v2/log?after=<seq>` returns entries in order. Clients cache the verified state and verify only new entries.

### 3.5 Pinning, rollback and fork detection

Each client stores per server: `server_id`, the highest verified `seq`, and its `entry_hash` (the **head**).

1. **Pinning.** `server_id` is fixed when a server is first added (from the invite link, 5.2, or from the blob for new devices, 7.3). On every connection the client fetches entry 0, computes its hash, and compares with the pin. A mismatch is a hard stop: "This is not the server you joined." There is no override except removing the server and adding it again.
2. **Rollback.** A client never accepts a log whose head `seq` is lower than the one it has stored, nor one where entry `seq` differs in hash from what it stored. Either is shown as "Not verified" with the reason "server changed history."
3. **Cross-checking through signed messages.** Every message and epoch header carries `log_seq` (the highest log entry its author had verified) and every message carries `log_head8` (first 8 bytes of that entry's hash). A reader who has verified a different hash at that `seq` has seen a fork: show "Not verified", keep both entries as evidence, offer to export them. A reader who sees `log_seq` above their own head must fetch the missing entries; if the server withholds them for more than 30 seconds, the reader treats the server as hiding changes (level "Not verified").
4. **Fresh heads.** A client that has not obtained a log head from the server in the last 24 hours while online shows "Not verified" until it does.
5. **Residual.** A server that shows two groups of members different logs from the first moment (a split view that predates any cross-group message) is not detected until a message or epoch header crosses between the groups. See threat model L7.
6. **Moving servers.** The owner can publish a new `origin_hint` (`server_meta`). A client follows only a new origin that is named in a verified entry. If the old host is gone, the user adds the server again from a new invite link; the embedded `server_id` matches, so the client merges it with the existing entry.

The server does **not** have a separate identity key. Its identity is the genesis hash, which is signed by the owner. (DECISIONS item 8.)

## 4. First-admin bootstrap

State machine of a fresh server: `UNCLAIMED → CLAIMED`. There is no way back.

1. On first start with an empty log, the server generates `setup_token` (16 random bytes, base32), stores only `H("hc/v1/setup-token", token)`, prints the token once to its console and log file, and serves `GET /v2/server` with `{state:"unclaimed"}`. It generates its OPAQUE `ServerSetup` (2.5). It does **not** generate a host key (15.3).
2. The person who runs the server opens a client at the server's address, creates or reuses an account on the device, and enters the token. The client:
   1. builds the genesis entry (3.3 kind 0) with the owner's `AccountPub`, a chosen username, the server name and `origin_hint` equal to the address used;
   2. runs OPAQUE registration for the owner (2.2) with `server_id` computed from the genesis hash it just built;
   3. sends `POST /v2/claim { setup_token, genesis, reg_upload, blob, device_cert }`.
3. The server checks the token with a constant-time compare, checks the genesis (valid signature, all features off, no host key), stores everything, deletes the token hash, and becomes `CLAIMED`. A second claim returns 409 forever.
4. The client then submits the first ordinary entries: `channel_create` for "General" (public) and authors that channel's epoch 0 (9.2).
5. The client shows the owner the `server_id` as a fingerprint and tells them it is inside every invite link.

Protections: the token is single use, 128 bits, and the endpoint is rate limited (18). After 10 wrong tokens the endpoint locks until the process restarts. The claim endpoint accepts requests only over TLS or loopback. If the console output is read by someone else before the owner claims, that person becomes the owner: the instructions must say to claim immediately and not to paste the log anywhere.

## 5. Joining

### 5.1 Two ways in

- **Invite link**: the admin creates it in advance; an admin does not need to be online when it is used.
- **Join request**: someone with only the server address asks; an admin approves.

Both end with a log entry that every client verifies.

### 5.2 Invite link and certificate

The admin's device creates `token_seed` (32 random bytes) and derives an Ed25519 key pair from it (`token_priv`, `token_pub`). It signs:

```
InviteCert = SignedObject under the admin's ak_sign, label "hc/v1/invite-cert"
payload { 1 v:1, 2 server_id:bstr32, 3 invite_id:bstr16, 4 issuer:account_id,
          5 token_pub:bstr32, 6 history:"full"|"from_now", 7 expires_at:uint,
          8 note:text≤64 }
```

It uploads the `InviteCert` to the server (`POST /v2/invites`) and shows the link:

```
housecall://join?o=<origin>&s=<server_id base32>&i=<invite_id base32>&t=<token_seed base32>
https://<origin>/join#o=…&s=…&i=…&t=…        (web form; everything is in the fragment so it is never sent to a server)
```

`token_seed` never goes to the server. The server holds `InviteCert` only, which contains `token_pub`.

**Why this shape.** The link carries (a) the server's identity (`s`), so first contact is pinned to what the admin saw; (b) a secret that only the link's holder can use. The join signature (`invite_pop`) is made with `token_priv`, which the server never saw, so the server cannot make its own join for this invite, and it cannot replace the joiner's public key without breaking the signature.

### 5.3 State machine: joining with an invite

```
[none] --client has link--> CONNECT
CONNECT: fetch GET /v2/server; compare entry-0 hash to `s`; mismatch → STOP (hard error)
       fetch & verify the log; fetch InviteCert (GET /v2/invites/<i>); verify issuer signature,
       issuer is admin/owner now, token_pub matches the one derived from `t`, server_id matches
REGISTER: OPAQUE registration (2.2) → reg_upload, blob
SUBMIT: build member_join entry (3.3 kind 2), sign with ak_sign, invite_pop with token_priv;
        POST /v2/join { entry, reg_upload, blob, device_cert, display, device_name }
        server checks: invite exists, not revoked, unused, not expired, username free & not banned,
        rate limits (18). Appends entry. → JOINED
JOINED: client fetches log, verifies its own entry, then fetches wraps (9.5).
        if history = "from_now": the member sees content only from the next epoch of each channel (9.4)
        if history = "full":     an existing member's device sends HistoryGrants (9.6) when online
```

Failure cases: invite expired/used/revoked (409/410, message "invite no longer valid"); username taken (the user picks another; nothing was written); log shows the entry in the wrong state (client stops and warns).

### 5.4 State machine: joining without an invite

```
REQUEST → PENDING → APPROVED | DENIED | EXPIRED
```

1. REQUEST. Client does OPAQUE registration (2.2) and sends `POST /v2/join-requests { username, display, account_pub, device_cert, reg_upload, blob, pop, note≤140 }`. `pop` = `Sign(ak_sign, "hc/v1/join-pop", H(server_id, username, AccountPub))`. The server returns `{request_id, pending_token}` (a random bearer used only to poll this request).
2. The client computes and shows the **join code**: `H("hc/v1/sas", "join", request_id, AccountPub)` mapped to 6 words from the BIP-39 list (66 bits; a 44-bit code could be ground by a hostile server in days). It says: "Read these words to the admin."
3. An admin's client shows the pending request: username, display, note, fingerprint, and a field for the 6 words. The admin enters the words the requester reads out. The client computes the code from the `account_pub` the **server supplied** and compares. A mismatch means the server swapped the key; approval is blocked and the request is flagged. There is no "approve without checking" button.
4. On match the admin chooses history (`full` / `from now on`, default `from now on`) and the admin's device signs `member_add` (3.3 kind 1) including the `pop` from the request. The server appends it; the request becomes `APPROVED`.
5. DENIED: the server deletes the request, the record and the blob. EXPIRED: after 7 days, same.

Pending requests: at most 20 per server and 1 per username; the pending record, blob and OPAQUE upload are held in a pending table and become real only when the `member_add` entry exists.

Why the code: without it a server that controls the join-request channel could substitute its own key and the admin would sign a ghost. With the invite path the signature by `token_priv` plays the same role.

### 5.5 History choice

The history mode is part of the signed entry (`member_add.history`, from the invite for `member_join`). It decides which epochs the newcomer receives for each public channel (9.4, 9.6). It is never decided by the server.

## 6. Sessions

### 6.1 Normal session

A device authenticates by signing a server-supplied challenge with `DK`. There are no long-lived bearer secrets and no cookies.

```
C→S  POST /v2/session/challenge { device_id }
S→C  { nonce: bstr32, server_time }
C→S  POST /v2/session { device_id, nonce, sig }
        sig = Sign(DK, "hc/v1/dev-session", H(server_id, origin, device_id, nonce))
S→C  { token: bstr32, expires_at }
```

- The server checks that the nonce is its own, unused and under 60 seconds old; the device is registered and `active`; the signature verifies against the stored `device_pub`. It stores `SHA-256(token)` only.
- `server_id` and `origin` in the signed data stop a hostile server from forwarding a challenge it got from the client to a different server.
- The token is sent as `Authorization: Bearer <token>` and in the WebSocket handshake. TTL 15 minutes. The client renews by repeating the exchange (also in-band on the WebSocket: `{t:"reauth", nonce, sig}`). Nothing is renewed silently without a signature.
- Revoking a device (7.4) marks it `revoked`, deletes its tokens and closes its sockets immediately.
- `X-Device-Key` (the current design) is removed.

### 6.2 State machine

```
NO_SESSION --challenge/sign--> ACTIVE --TTL or revoke--> NO_SESSION
ACTIVE --reauth OK--> ACTIVE (new expiry)
```

### 6.3 Pending session

After an OPAQUE login by an unregistered device (7.2), the token has scope `pending`: it can only call `GET /v2/devices/pending/<id>` and `DELETE` the same request. Everything else is 403.

### 6.4 Transport

TLS only, except loopback for local development. Clients refuse `http://` to any other host. The server sends strict security headers on every response: the current header set in `server/src/lib.rs` plus `'wasm-unsafe-eval'` in `script-src` (the crypto WASM needs it), `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `Strict-Transport-Security`. The LiveKit signalling and the TURN endpoints are reached through the same origin by the reverse proxy so `connect-src 'self'` stays strict.

## 7. Multiple devices and device approval

### 7.1 Device registry

Server table per account: `{device_id, device_pub, cert, name, created_at, last_seen, status: active|revoked}`. Names are shown to the user, so they are plaintext to the server. Maximum 10 active devices.

### 7.2 Sign-in on a new device

Inputs: server address, username, password. If the user wants a pin, they can paste the server fingerprint; otherwise, see 7.3 for where the pin comes from.

After `login_ok` (2.4) the server decides:

- The account has **no active device** (for example the user signed out of their only device): `granted`. The blob is returned immediately. This is the "password alone works only when no other device exists" case.
- The account has one or more active devices: `approval_required`.

### 7.3 State machine: device approval

```
LOGIN_OK(approval_required) → PENDING(pending_id) → APPROVED | DENIED | EXPIRED | AUTO_APPROVED
APPROVED/AUTO_APPROVED → REGISTER → ACTIVE
```

1. **PENDING.** The server creates `{pending_id, device_pub, device_name, created_at, expires_at = +10 min, auto_at = +7 days, source_ip_class}` and notifies every active device (WebSocket, and push if on). The new device shows a 6-digit **code**: `u32be(first 4 bytes of H("hc/v1/sas", "device", device_pub, pending_id)) mod 1000000`, zero-padded (TV-12). The new device polls `GET /v2/devices/pending/<id>`.
2. **Approver.** An existing device shows: device name, time, approximate network location of the request, and asks the user to **type the 6-digit code shown on the new device**. The approver's client computes the code from the `device_pub` the server gave it and compares with the typed code. On match, it signs:
   - `DeviceApproval = Sign(DK_approver, "hc/v1/dev-approve", H(server_id, pending_id, device_pub, approver_device_id))`
   - `DeviceCert` for the new device (1.2), signed by `ak_sign` (the approver holds `RS`).
   and sends both to `POST /v2/devices/pending/<id>/approve`. The server verifies the approval signature against an **active** device key of the same account, then marks the request `APPROVED`.
3. **Release.** On `APPROVED` the server returns `{blob, cert}` to the pending session. The new device decrypts the blob with its `export_key`, derives `AccountPub`, compares it with the cert and with the log (2.3), and calls `POST /v2/devices` to register `device_id`, `device_pub`, `cert`. The server activates it. The device then fetches `State` (7.5), which holds the pins this account recorded earlier, and compares the `server_id` pin for this server with entry 0 of the log it just verified; a mismatch is a hard stop. If the state has no pin (first device on this server), the device pins now.
4. **DENIED.** An approver can deny; the request is deleted; the account gets a 24-hour cooldown for new requests; all devices are told.
5. **EXPIRED.** After 10 minutes the request can no longer be approved by a device (the approver is expected to be present). It is not deleted; it stays pending for auto-approval.
6. **AUTO_APPROVED.** Seven days after `created_at`, if nobody denied, the server releases the blob exactly as in step 3 but without a `DeviceApproval`. Every active device is notified when the request is created, once a day, and when it auto-approves. The device list marks the new device "approved by waiting period". This path exists so that a user who lost their only device and has no recovery phrase can still get in with the password; the delay is the price. (DECISIONS item 14.)
7. **Pin on a new device.** On first contact the device has no earlier knowledge of this server. It relies on TLS plus OPAQUE (a server that does not hold the record cannot complete login). A hostile server that does hold the record is treated as "the server" (threat model A2). Pins carried in `State` protect later devices.

**What the code is and is not.** The 6-digit code has about 20 bits. It makes the approver prove they are looking at the screen of the device that is asking, which defeats an attacker who has only the password. It does **not** defend against a malicious server, which can grind a key pair whose code matches in about a million tries.

**What approval is.** Approval is enforced by the server. It is not cryptographic: the blob is encrypted under the password alone. A malicious or breached server that has the user's password (or cracks it offline, L2) obtains the blob without any approval. Approval defends against the **stolen password with an honest server** case, which is the common one. This is stated to users nowhere in the UI (D6); it is stated in the threat model.

Rate limits on pending requests: 18.

### 7.4 Revoking a device

From another device (or the device itself): `DELETE /v2/devices/<device_id>` with a normal session. Effect: sessions closed, `DK` rejected. A user who suspects theft of an unlocked device should use "Secure my account" (8.4), because revoking does not remove `RS` from the device.

### 7.5 Account state blob (private, synced)

Per server, an opaque blob `State { version:uint, nonce, ct }` where `ct = AEAD(K_state, nonce, CBOR(state), aad = H("hc/v1/state", server_id, account_id, u32be(version)))`. Content: server pins, friend list and petnames, per-channel notification settings, read pointers, bot-notice flags. Written with compare-and-swap on `version`. Merge rule across servers: per-record last-writer-wins by `(lamport, device_id)`; friend records merge by union with state precedence `blocked > friend > pending`. The server sees its size and update times.

## 8. Recovery, lost password, account key replacement

### 8.1 Recovery phrase

Offered at account creation, skippable. The phrase is the 24-word BIP-39 encoding of `RS` (256 bits plus checksum). The client shows it once, asks the user to confirm three randomly chosen words, and states: "Anyone with these words is you." It is never stored by the client and never sent anywhere. It cannot be changed without changing `RS` (8.4).

### 8.2 Using the phrase on a new device

```
C→S  POST /v2/recover/challenge { username }              → { nonce }
C→S  POST /v2/recover { username, nonce, device_pub, device_cert, device_name,
                        sig = Sign(ak_sign, "hc/v1/recover", H(server_id, nonce, device_pub)) }
```

The server verifies `sig` against the stored `account_pub` for that username. On success it registers the device with no approval and no password. The client then sets a new password (OPAQUE registration, authorised by a signature from `ak_sign` over the registration upload and a new blob). A phrase holder is the account; the phrase is the strongest credential and has no rate limit beyond the generic one.

### 8.3 Forgot the password, no phrase, no usable device

The user has no `RS`. They create a new account key (new `RS'`, new identity) with the same username and ask an admin.

```
C→S  POST /v2/replace-requests { username, new_pub, new_pop, device_cert, reg_upload, blob, note }
```

An admin's client shows: "Alice says they lost their password. Old fingerprint X, new fingerprint Y. Confirm with Alice in person or by phone, then compare these six words." The word check is the same as in 5.4 (computed from `new_pub`). The admin chooses history `full` or `from_now` and signs a `key_replace` entry (3.3 kind 14, no `old_proof`). Effects:

- The old account is removed; **all epochs it was in rotate** (9.3 trigger `member_removed`).
- The new account is added with the chosen history. With `full`, an existing member's device wraps the old epochs' keys to the new key (9.6). With `from_now`, the user starts empty.
- Direct messages: the user's old DM threads cannot be read by the new identity. The people they talked to see a new contact claiming the name and must accept it (13.6). Old history in DMs stays unreadable to the user.
- Anyone who could talk the admin into this can take over the username. The admin UI says so in one sentence.

### 8.4 "Secure my account": replacing the account key from a good device

Used after theft of an unlocked device, or after the recovery phrase leaks. The user's good device creates `RS'` and a new device key, and for each server sends a `key_replace` request that **includes `old_proof`** (a signature by the old `ak_sign`, showing the old key is under the requester's control). The admin approves as in 8.3 (an attacker who holds the old key may also send a replace request; two conflicting requests for one username are shown to the admin as a warning). After this, the old key is a removed member: epochs rotate and it cannot read new content. It can still read everything it had keys for. The user's good device still holds the old epoch keys and can grant them to the new key when the entry says `history: full`. Contacts see "key changed" and must re-verify (13.5).

## 9. Channel epochs, wraps, rotation

### 9.1 Objects

A channel's content is encrypted under an **epoch key** `EK_n` (32 random bytes, generated by the device that creates epoch `n`). Epoch `0` is created when the channel is created. A new epoch is created whenever the readers of future content must change (9.3).

Class keys derived from `EK_n` (HKDF-SHA256, salt = `channel_id`):

| Key | Label | Who may hold it |
|---|---|---|
| `K_text` | `KDF(EK_n, channel_id, "msg/t", u32be(n), 32)` | Every reader. The host only if a text feature is on (15). |
| `K_file` | `… "msg/f" …` | Every reader. The host only if a file feature is on. |
| `K_url` | `… "msg/u" …` | Every reader. The host only if link preview is on. |
| `K_eph` | `… "eph" …` | Every reader (typing indicators) |
| `K_call` (not a key itself, see 12) | uses `EK_n` directly | Members and bots only. Never the host. |

The host can never hold `EK_n`, so it can never derive `K_call` or the other classes.

```
EpochHeader = SignedObject under the author's ak_sign, label "hc/v1/epoch-header"
payload { 1 v:1, 2 server_id, 3 channel_id, 4 epoch:uint, 5 prev_hash:bstr32,
          6 log_seq:uint, 7 reason:uint, 8 recipients:[account_id…],
          9 host: null | {key_id:bstr16, classes:uint},     classes bit 1=T, 2=F, 4=U
         10 checks: {0: bstr16, 1?: bstr16, 2?: bstr16, 4?: bstr16},
         11 author:account_id, 12 created_at }
header_hash = H("hc/v1/epoch-header", payload, sig)
check_k = first 16 bytes of HMAC-SHA256(key_k, "hc/v1/key-check")        key_0 = EK_n; key_1 = K_text; key_2 = K_file; key_4 = K_url
prev_hash = header_hash of epoch n-1 (zero for epoch 0)
reason: 0 create, 1 member_removed, 2 member_added_from_now, 3 feature_change, 4 manual, 5 bot_change, 6 key_replace
Wrap { 1 header_hash, 2 recipient:account_id|"host", 3 class:uint (0=EK, 1=T, 2=F, 4=U), 4 enc:bstr, 5 ct:bstr }
  HPKE base mode, recipient's ak_dh (or the host key), info = H("hc/v1/wrap", header_hash, recipient, class), aad = header_hash,
  plaintext = the 32-byte key.
```

The wrap itself is not signed. Authenticity comes from `header_hash` being in HPKE `info` and `aad`, and from `check_k` inside the signed header: a recipient decrypts, computes the check, and compares with the header. A server that substitutes a different key in a wrap is detected here.

### 9.2 Creating an epoch (author's steps)

1. Verify the log up to its head (3.5). Compute the **expected recipients** for this channel at that `log_seq`:
   - Public channel: all non-removed human members (roles owner, admin, member), plus bots explicitly added to this channel.
   - Private channel: the creator, members added by `channel_member_add`, plus bots explicitly added.
   - Never: removed, banned, or replaced accounts; accounts that joined `from_now` after this header's `log_seq`.
2. Compute the **expected host classes** (15.2). Always empty for private channels and DMs.
3. Generate `EK_{n+1}`; derive class keys and checks.
4. Build and sign the header; build one HPKE wrap per recipient (class 0), and one wrap to the host key per class in `host.classes`.
5. `POST /v2/channels/<id>/epochs { header, wraps }`. The server accepts only epoch `n+1` where `n` is its current epoch (compare-and-swap); else 409.

### 9.3 When to rotate

| Trigger | Required by |
|---|---|
| Member removed, banned, left, or replaced (`member_remove`, `key_replace`) | Every channel they could read (public: all; private: those they were in) |
| Private channel member removed or left | That channel |
| Bot removed from a channel | That channel |
| Host feature change that changes `host.classes` or `host.key_id` | Every public channel |
| New member joined with `from_now` | Every public channel (the newcomer must not read earlier epochs) |
| Manual (admin or private-channel creator) | That channel |

There is no periodic rotation. Random 192-bit nonces mean an epoch has no message-count limit.

Rotation is **eager for the signer and lazy for everyone else**:

- The device that signs the triggering log entry rotates every affected channel that has had a message in the last 30 days, in the background.
- **Mandatory before send.** A client must not encrypt a message under epoch `n` if the verified log contains a membership or feature change affecting that channel at a `seq` greater than epoch `n`'s `log_seq`. It first creates epoch `n+1`. If the server will not accept the new epoch, sending fails with "Can't secure this channel right now". It never falls back to the old epoch.
- **Active calls.** Any client in a call on a channel that sees a removal affecting it rotates that channel within 5 seconds (jitter by rank of `account_id`, so one winner) and then re-keys the call (12.3).
- **Concurrent rotations.** The server's compare-and-swap picks the first header for each `(channel, n+1)`. A loser that sees a different valid header adopts it, then re-evaluates whether it still meets the expected recipients and features; if not it creates `n+2`.

### 9.4 Verifying and adopting an epoch (reader's steps)

A client adopts a header only if all of these hold, else it ignores it and flags the server:

1. The signature verifies and `author` is a current member of the channel in the verified log at `log_seq`.
2. `recipients` equals exactly the expected recipients at `log_seq` (not a superset, not a subset). A superset is the ghost-member signature.
3. `host` equals exactly the expected host classes and `key_id` the log's current host key (15). A header with a host entry the log does not authorise is rejected.
4. `epoch` is `prev + 1` and `prev_hash` matches the header it already holds; `epoch` is higher than the highest the client has stored for the channel (rollback guard); `log_seq` is not lower than the `seq` of the last log entry affecting this channel that the client has verified.
5. Its own wrap decrypts, and `check_0` matches `HMAC(EK, …)`.
6. If the client has already stored a different header for the same `(channel, epoch)` it flags **equivocation** and keeps the first.

A new device of an existing member has no stored epochs. It downloads the account's wraps, then applies rules 1 to 5 per header and a further rule: the **latest** header's `log_seq` must be at least the `seq` of the last log entry affecting the channel (otherwise the server is showing an epoch from before a removal, and the device refuses to send and shows "Not verified").

### 9.5 Receiving keys

`GET /v2/wraps?since=<cursor>` returns the account's wraps and headers. The device decrypts each with `ak_dh`, verifies as in 9.4, stores `EK_n` locally (encrypted at rest with a key in the secure store) and keeps all epoch keys it has been granted.

### 9.6 History grants

For `history: full`, existing members hand the newcomer the older epoch keys.

```
HistoryGrant = SignedObject under the grantor's ak_sign, label "hc/v1/grant"
payload { 1 v:1, 2 header_hash:bstr32, 3 recipient:account_id, 4 log_seq:uint, 5 grantor:account_id }
+ Wrap { header_hash, recipient, class 0, enc, ct }
```

Valid only if the log shows `recipient` is a member whose entry says `history: full` (or a private-channel add with `history: full`) at or before `log_seq`, the grantor is a current member holding that epoch, and the recipient's check matches (`check_0`). A `from_now` member receives nothing older than the first epoch that lists them. Grants are issued by whichever member device first comes online and sees an outstanding full-history member; duplicates are harmless.

If no current member still holds an old epoch (all their devices were lost), that epoch is gone for newcomers. This is availability, not safety.

### 9.7 State machine per channel (client view)

```
NO_KEYS → HAVE_EPOCH(n)
HAVE_EPOCH(n) --verified log change affecting channel--> STALE(n)      send blocked
STALE(n) --create or adopt epoch n+1 meeting expected set--> HAVE_EPOCH(n+1)
STALE(n) --server refuses new epoch--> STALE(n)                         "can't secure this channel"
HAVE_EPOCH(n) --header n+1 with unexpected recipients or host--> ALERT  keep n, flag server
```

## 10. Messages

### 10.1 Envelope

```
Message = SignedObject under the sender's ak_sign, label "hc/v1/msg"
payload {  1 v:1,
           2 msg_id:bstr16,
           3 channel_id:bstr16,
           4 epoch:uint,
           5 sender:account_id,
           6 device_id:bstr16,
           7 sender_seq:uint,            per (sender, device, channel), starts at 1, +1 per message incl. edits, reactions
           8 log_seq:uint,
           9 log_head8:bstr8,
          10 sent_at:uint,
          11 kind_hint:uint,             0 normal, 1 edit, 2 delete (these two carry target)
          12 target?:bstr16,
          13 mentions:[account_id],       clear text on purpose, see 19.1
          14 nonce_t:bstr24, 15 ct_t:bstr,
          16 nonce_f?:bstr24, 17 ct_f?:bstr,
          18 nonce_u?:bstr24, 19 ct_u?:bstr }
```

The server adds `server_seq` (per channel, assigned at accept) and `received_at`. They are not signed and not trusted for anything but ordering display.

### 10.2 Encryption

For each present class `c ∈ {t, f, u}`:

```
mk_c = KDF(K_c, salt = msg_id, label "mk", channel_id, u32be(epoch), sender, 32)   per-message key
ct_c = AEAD(mk_c, nonce_c, pad(plaintext_c),
            aad = H("hc/v1/msg/" ‖ c, server_id, channel_id, u32be(epoch), msg_id, sender))
```

- `pad`: append `0x80` then zeros to the next multiple of 256 bytes. The reader strips from the end up to the last `0x80`. (Hides exact length only coarsely.)
- Per-message keys exist so a reporter can disclose one message to an admin (10.8) without disclosing the epoch.
- Plaintext structures:
  - `t`: `{1 kind, 2 body:text, 3 reply_to?:msg_id, 4 channel_meta?, 5 call?, 6 emoji?, 7 pinned?:bool, 8 embeds?:[{url,title,desc}]}`; kinds: 0 text, 1 edit, 2 delete, 3 reaction on, 4 reaction off, 5 pin, 6 channel_meta (name, topic: the channel's name is a message), 7 call_start, 8 call_rekey, 9 call_end.
  - `f`: `{1 attachments:[{file_id, blob_id, size, chunk, key:bstr32, name, mime, thumb?:{blob_id,key,w,h}}]}`
  - `u`: `{1 urls:[text]}` (the URLs the sender wants previews for; used only by the host link-preview feature, 15)

### 10.3 Sending

1. Channel is `HAVE_EPOCH(n)` (9.7). Take the highest verified epoch.
2. Fill `sender_seq`, `log_seq` (own verified head), `log_head8`, `msg_id`, `nonce`s.
3. Encrypt classes, build payload, sign.
4. `POST /v2/channels/<id>/messages`. The server checks: session, channel membership (from its log view), `epoch` equals the current epoch (else 409 "stale epoch", the client rotates or re-fetches and retries), `sender` matches the session's account, size limits, `msg_id` unused. It stores the bytes and fans out.

### 10.4 Receiving and verifying

A reader accepts a message only if:

1. The signature verifies under the sender's `ak_sign` from the verified log, and `sender` was a member of the channel at `log_seq` per the log.
2. `epoch` is an epoch the reader holds; decryption succeeds with the AAD above.
3. `msg_id` is new (else drop; same `msg_id` with different bytes is equivocation).
4. `(sender, device_id)`'s `sender_seq` is greater than the last accepted one for live messages; a gap is shown as "1 message missing" (the server may be dropping messages); a repeat or lower number is dropped. Backfilled history is ordered by `server_seq` and gaps are flagged the same way.
5. `log_head8` agrees with the reader's verified hash at `log_seq` (3.5 item 3).
6. **Live messages to a stale epoch are dropped.** If the reader has adopted epoch `m > epoch`, a live message arriving in epoch `epoch` is dropped (the sender is told to retry). Backfilled history is exempt.
7. `sent_at` more than 10 minutes from the reader's clock is displayed with "time unverified".

Edits (`kind 1`) and deletes (`kind 2`) are valid only if `sender` equals the target message's sender (or the sender is an admin or owner who is a member of the channel, for moderation). Among edits of one target, the edit with the highest `sender_seq` from that sender wins; an older edit arriving later is ignored. A delete is final: a message that was deleted stays deleted when it, or an older edit of it, is replayed. Reactions and pins are messages too, so the server cannot see who reacted to what.

### 10.5 What the signature does and does not give

It gives non-repudiable authorship inside the group (a member cannot deny sending, and the server cannot forge). Non-repudiation is a deliberate choice; deniability is not provided (threat model L9).

### 10.6 Ordering, replay, reordering

- Replay of an old message into the same channel: same `msg_id` → dropped. Into another channel or epoch: `channel_id`/`epoch` are in the signed payload and in the AEAD AAD → fails.
- Reordering and dropping by the server: detectable only as gaps and out-of-order `sender_seq` per sender. Total order across senders is whatever the server says. Timestamps are claims.
- Delay: a delayed message is displayed with `sent_at` vs `received_at`.

### 10.7 Channel names and topics

A public channel's display name and topic are `channel_meta` messages in that channel (class `t`), so the host sees them only if a text feature is on. The server still needs a label for its own UI; the owner-visible server console shows channel ids, not names. Clients show the latest `channel_meta` from a member who is an admin or the channel creator.

### 10.8 Reporting a message

The reporter's client sends the admins a `Report { message: SignedObject (the original bytes), mk_t, [mk_f], context: [more messages with their mks], note }`. An admin's client verifies the sender's signature on each message and decrypts with the disclosed per-message key. The reporter cannot invent content (it is signed by the sender) and discloses nothing else of the epoch. A report can omit messages (selective reporting). Admins cannot read DMs or private channels they are not in, except through a report.

### 10.9 Ephemeral events

Typing indicators are `{channel_id, epoch, sender, nonce, ct}` with `ct = AEAD(K_eph, …)`, not signed, not stored, rate limited to one per 3 seconds per channel. The server sees the event and its size.

### 10.10 Read state

Per-channel read pointers live in the encrypted account state (7.5). Unread counts are computed on the device. The server does not know what a user has read.

## 11. Attachments

1. The sender generates `file_key` (32 random bytes) and `file_id` (16 random bytes). Thumbnails and previews are made by the sender's client before encryption.
2. The blob is `"HCF1" ‖ u32be(chunk) ‖ nonce_prefix(19)` followed by chunks. Chunk `i` (0-based) of plaintext size `chunk` (last chunk shorter or equal, never empty unless the file is empty) is encrypted with XChaCha20-Poly1305, nonce = `nonce_prefix ‖ u32be(i) ‖ last_flag(1 byte: 1 for the last chunk, else 0)` (this is the STREAM-BE32 layout in `aead::stream`), key = `file_key`, aad = `H("hc/v1/file", file_id)`. Each chunk on disk is ciphertext ‖ 16-byte tag. A decryptor that does not see a chunk flagged last, or sees a chunk after it, reports truncation or extension.
3. Random access (media seeking) decrypts chunk `i` by building its nonce from the layout above; the chunk's offset is `header + i × (chunk + 16)`.
4. Upload: `POST /v2/blobs { channel_id, size }` → `blob_id`; `PUT /v2/blobs/<id>` with the bytes (resumable by offset, as today). The server checks membership and the cap; it stores the bytes as given. The existing server-held `HOUSECALL_MEDIA_KEY` encryption becomes optional extra at-rest encryption (it protects nothing from the host, which can read the blob anyway, but the blob is already ciphertext).
5. The descriptor (with `file_key`, name, mime, size) is in the message's `ct_f` (10.2). The server never sees `file_key`.
6. Download: `GET /v2/blobs/<id>` with Range support. A client verifies every chunk on read; a bad tag aborts and shows "file was altered".
7. Deleting a message deletes its blobs on the server (authorised by the delete message's outer `target`, 10.1). This is best effort and not erasure (threat model L10).
8. Clients show the real size and file type, never auto-open and never execute files. No server malware scanning exists unless the owner enables the scan feature (15), and even then the verdict is advisory.

## 12. Calls

### 12.1 Model

Audio and video go through LiveKit (SFU plus TURN). The SFU forwards media it cannot decrypt. Encryption is LiveKit's frame encryption (AES-GCM on encoded frames) with keys that this protocol supplies. Nothing about call keys is chosen by the server.

### 12.2 Key derivation

```
call_id      = 16 random bytes, chosen by the first participant and announced in a signed
               channel message of kind 7 (call_start) containing {call_id, epoch, generation 0}
room_name    = base32( KDF(EK_n, salt=call_id, label "room", channel_id, 16) )     what the SFU sees
ck_{n,g}     = KDF(EK_n, salt=call_id, label "call", channel_id, u32be(n), u32be(g), 32)
sender_key(p)= KDF(ck_{n,g}, salt="", label "call/sender", participant_identity(p), 32)
participant_identity = hex(account_id[0..16]) ‖ "." ‖ hex(device_id)
```

Each sender encrypts with `sender_key(self)`; receivers derive `sender_key(p)` for each participant `p` from the LiveKit identity. LiveKit's `BaseKeyProvider` in per-participant mode with key index `g mod 16` is expected to carry this (spike: confirm in all five webviews and the Rust SDK for Steve). The LiveKit access token is minted by the server (`POST /v2/channels/<id>/call/token`) for a verified member; the identity in the token must equal `participant_identity` and the client checks its own and others' identities against the log.

Consequences: a participant whose identity is not a member in the log is shown as "unverified participant" and cannot decrypt anything (it has no key). Any member can derive the key of any other member, so media inside a call is authenticated to "a member of this channel", not to a particular person. A hostile SFU cannot swap identities without making decryption fail.

### 12.3 Re-keying

- Join: a participant who joins mid-call derives `ck` for the current `(n, g)` announced in the latest `call_start` or `call_rekey` message. Late joiners cannot decrypt earlier media (no one records it).
- Leave: no re-key (a leaver is still a channel member and can derive the key of any call in the channel).
- **Epoch change** (member removed, banned, left; bot removed; from-now join): after adopting epoch `n+1`, a participant sends `call_rekey {call_id, epoch: n+1, generation: g+1}` (a signed channel message), sets the new sender key at index `(g+1) mod 16`, switches sending to it immediately, and keeps decrypting with the old key for 10 seconds for in-flight frames. The first rekey message seen for a given `generation` wins.
- The server removes the removed member from the LiveKit room (availability). Confidentiality relies on the re-key, not on the removal.
- Not provided: re-keying on a timer, forward secrecy inside a call, hiding who speaks or their bitrate from the SFU.

### 12.4 Data and metadata

LiveKit data packets are not used for anything sensitive; reactions and hand-raises are channel messages (10). The SFU sees: room name, participant identities, join and leave times, which tracks exist and their sizes and rates, active-speaker information, IP addresses and the TURN allocations.

### 12.5 DM calls

DM and group-DM calls use the same derivation with the DM or group DM's epoch key.

### 12.6 Server-played media

A Plex watch stream or a Shared Browser tile is created by the host. It is not end-to-end encrypted and is labelled in the call UI (SECURITY-LEVELS 9). It does not touch call keys.

## 13. Friends, DMs, group DMs, impersonation

### 13.1 Reaching someone

You can reach an account if you and they share a server. The shared server is the **home server** of the conversation. The UI never shows the server name in the normal path. If two accounts share several servers, the client picks one (the one with the longest shared history, then the lowest `server_id`) and stores the choice in its state.

The key the client uses for the other person is the `AccountPub` from the shared server's **verified log** (the admins signed that username to that key). If the two accounts share several servers, the client checks that every shared log lists the same `AccountPub` for that `account_id` (they must, since `account_id` is a hash of the key; what can differ is the username). A different key behind the same displayed username or friend name is a warning, not a merge (13.6).

### 13.2 Friend request and acceptance

```
FriendRequest = SignedObject under the sender's ak_sign, label "hc/v1/friend-req"
payload { 1 v:1, 2 from:AccountPub, 3 to:account_id, 4 via_server:server_id,
          5 username_seen:text, 6 display_seen:text, 7 message?:text≤140, 8 nonce:bstr16, 9 created_at }
FriendAccept  = SignedObject, label "hc/v1/friend-acc", payload { v, from:account_id, to:account_id,
          request_hash:bstr32, created_at }
```

Each is sealed to the recipient: `HPKE(to.ak_dh, info = H("hc/v1/mail", from_id, to_id), plaintext = the signed object)` and delivered through the shared server's mailbox: `POST /v2/mail { to, sealed }`. The server sees sender, recipient, size and time. It enforces: both are current members; rate limit; the recipient has not blocked the sender.

The recipient verifies the signature, that `from` hashes to the sender id the server claims, and that this account is a member of the shared server per the log. The UI shows `display_seen` and `username_seen` as **claims** next to the fingerprint-derived colour avatar. Accepting creates a friend record in the encrypted state (7.5) with `first_seen_pub`.

### 13.3 DMs

```
DMCreate = SignedObject (initiator), label "hc/v1/dm", payload { v, dm_id, a:account_id, b:account_id,
           home_server:server_id, created_at }
DMAccept = same, signed by the other party
```

- `dm_id` is derived from the two account ids (0.5). One thread per pair per home server.
- The initiator authors epoch 0 with `recipients = [a, b]`, no host entry ever, and wraps to both `ak_dh` keys. The peer's client accepts the header only if the author is a party and `recipients` is exactly `{a, b}`.
- Messages and attachments are as in 10 and 11 with `channel_id = dm_id`.
- There is no admin and no log for a two-person DM: the set cannot change. If either side's account key is replaced, the new `account_id` produces a new `dm_id` and a new thread; the old thread stays on devices that have it.
- The home server enforces that both accounts are current members; if one leaves the server the DM stops routing there. The conversation can be restarted on another shared server as a new thread. History of the old thread stays readable on devices that kept it and not on new devices (the server no longer routes it for them). The UI says "Conversation moved" without naming servers.
- Host-assisted features never apply to DMs (15.2).

### 13.4 Group DMs (up to 10)

A group DM has its own mini log with the same entry format and its own `server_id` (the hash of its genesis, signed by the creator). Allowed kinds: `genesis` (creator), `member_add` (creator only; the added account must be a friend of the creator and a member of the home server), `member_remove` (creator, or self), `profile_set`. Everything else (epochs, messages, calls) is as for channels, with `log_seq` meaning this mini log. The creator is the only one who can add or remove people. A group DM must live on a server where every member is present; a member leaving that server is removed from the group by the server's routing and by an automatic `member_remove` signed by the creator's client when it sees it.

### 13.5 Safety numbers and key changes

`safety_number(a, b)` = decimal of `H("hc/v1/fp", min(a_pub,b_pub), max(a_pub,b_pub))`, first 15 bytes, in 6 groups of 5 digits. Shown in the contact screen with a "Mark as verified" button that sets `verified = true` in the friend record. When a friend's `account_id` for a username changes (13.6) the friend record is not updated; a new contact is created, flagged, and DMs to it stay in a new thread until the user accepts.

### 13.6 Username impersonation across servers

- Usernames are local to a server. `alice` on server A and `alice` on server B are different accounts unless their `account_id` matches.
- The unit of trust is `account_id`. A friend record stores `account_id` and a petname chosen by the user. Display names and usernames are shown only as "claimed".
- A friend request or a DM from an account whose username or display name equals that of an existing friend, but whose `account_id` differs, is shown as "**New contact using the name <name>. Not your friend <name>.**" with both fingerprints, and cannot be auto-accepted.
- Within one server, usernames are unique and lower-case ASCII, which rules out look-alike characters. Display names can imitate; the member list shows username under the display name, and the admin sees both on join approval.
- A server that serves a log in which a username maps to a different key than the one a friend recorded is exposed by 13.1: the client compares `account_id`s.
- Not provided: a global directory or any way to prove that "Alice" on two servers is the same human other than comparing fingerprints.

### 13.7 Blocking

Blocking sets `blocked` in the encrypted state and sends `POST /v2/mail/block { account_id }` so the server drops mail from that account to the blocker. A blocker can still be reached in shared channels; blocking hides their messages client-side.

## 14. Revocation, bans, moderation

| Action | Log entry | Crypto effect | Server effect |
|---|---|---|---|
| Leave | `member_remove` (self, `leave`) | Rotate affected channels | Drop sessions and mail |
| Kick | `member_remove` (`kick`) | Rotate affected channels | Drop sessions, remove from LiveKit room |
| Ban | `member_remove` (`ban`) | As kick; account id and username can never join again on this server | As kick, plus join rejection |
| Timeout | none | none | Server refuses posts and call tokens for a period. This is server policy, not cryptography: a malicious server can ignore it. |
| Delete a message (moderation) | message kind 2 by an admin who is a channel member | none | Ciphertext purged |
| Remove a device | none | none | Sessions closed; device key rejected (7.4) |
| Account key replace | `key_replace` | Rotate affected channels | Old account removed |
| Bot removal | `bot_channel_remove`, `member_remove` | Rotate that channel | Bot sessions dropped |

A removed member keeps every key it already had. It can read every message that was encrypted under those epochs, including ones it fetches later. It cannot read anything encrypted under later epochs (9.3 rules). A ban does not prevent a determined person from creating a new key and username; invite-only joining and the join-request code check are the barriers.

Admins moderate as members: they can delete messages and remove members in channels. They cannot read channels they are not in.

## 15. The host key and host-assisted features

### 15.1 Design in one paragraph

By default the server stores ciphertext only. The owner can turn on up to five **host-assisted features**. Turning one on is an owner-signed log entry that publishes a **host public key**. After the entry, clients that create new channel epochs for public channels add one HPKE wrap to the host key **for each key class the enabled features need** (not the epoch key). Only those class keys give the host access, and only to epochs created after the entry. Members see a banner and a lower security level derived from the same entry. Turning features off creates a log entry and new epochs without the host wraps, and the host key is destroyed when no feature needs it.

### 15.2 Features, key classes, scope

| Feature | Host needs | Class bit | What the host can read |
|---|---|---|---|
| `push_text` | Text of messages, to compose a sealed preview | T (1) | All message text, edits, reactions, channel names, replies and embeds in covered epochs |
| `search` | Text of messages, to build an index | T (1) | Same as above |
| `scan` | File bytes | F (2) | File names, types, sizes, file keys, thumbnails and the bytes of every attachment in covered epochs |
| `transcode` | File bytes | F (2) | Same as above; also writes derived files |
| `link_preview` | URLs to fetch | U (4) | Only the URLs the sender's client put in `ct_u`; and the fetched pages |

`classes` for a channel = the union of bits of enabled features. Text bodies are never readable through F or U, and files are never readable through T or U.

**Scope.** Features apply only to **public channels**. They never apply to private channels, DMs, or group DMs; those headers always have `host: null` and clients reject any header that says otherwise. Push for those is always content-free (17.2). (DECISIONS item 15; flagged for the owner.)

**State machine (owner view).**

```
OFF --owner enables first feature--> ARMING --host key published, log entry appended--> ON(features F)
ON(F) --owner changes the set--> ON(F') or OFF            (each change is one features_set entry)
ON(F) --owner rotates the host key--> ON(F) with new key_id
ON(F) --owner disables the last feature--> OFF, host key destroyed
```

Transitions are always a `features_set` entry (3.3 kind 9) signed by the owner's `ak_sign`. The server's console, config files and environment variables have **no** way to change the feature set; the server code must not read any such setting. A feature that the log says is off must not be active in the server process; a feature the log says is on is active only for epochs that carry the matching wrap.

### 15.3 Generating the host key

1. The owner's client asks `POST /v2/host/key {}` (signed by the owner's device session). The server must not already have an active host key.
2. The server generates an X25519 key pair (`getrandom`), `key_id` = 16 random bytes, and encrypts the private half for storage (15.4). It returns `{key_id, pub}`.
3. The owner's client builds the `features_set` entry containing `host_key: {key_id, pub}` and the chosen features, signs it, and submits it. Only the entry makes the key "published". If the entry is never submitted, the server deletes the unpublished key after 1 hour.

There is no host key on a server where features have never been enabled. A server with every feature off, after a disable, has no host key either.

### 15.4 Storing the host key at rest

```
HostKeyFile {  1 v:1, 2 key_id, 3 server_id, 4 mode:"file"|"passphrase", 5 salt?:bstr16,
               6 nonce:bstr24, 7 ct:bstr }
  wrap_key = KDF(WK, salt = key_id, label "host-at-rest", 32)       WK from 2.5
  ct = AEAD(wrap_key, nonce, host_private(32 bytes), aad = H("hc/v1/hostkey-file", key_id, server_id))
```

- `WK` is the server's at-rest wrap key (2.5), not stored on the data volume or in backups, in `file` mode as a separate root-owned file, in `passphrase` mode derived at start with Argon2id.
- The file lives in the data directory. It is useless without `WK`.
- The private key is held in process memory only while the host key is active and unlocked: pages are `mlock`ed where the OS allows, core dumps are disabled (`prctl(PR_SET_DUMPABLE, 0)` on Linux), memory is zeroized on drop, the key is never logged, never returned by any API, never put in an environment variable.
- Everything derived with host access that touches disk is encrypted: the search index, thumbnails, transcodes and preview cache are encrypted under `KDF(WK, salt=key_id, label "host-at-rest" ‖ feature name)` and deleted when the feature is turned off.
- Plaintext class keys the host unwraps are kept in memory only, for the life of the process, bounded by an LRU, and re-derived from the stored wraps on demand. They are not written to the database.
- In `passphrase` mode, after a restart the host is **locked** until the operator supplies the passphrase on the console. While locked, host features pause: push becomes content-free, search returns "unavailable", uploads are accepted but not scanned or transcoded (and the UI says so). Chat, calls and everything else work normally.

What this protects and what it does not: a stolen data volume, snapshot or backup does not yield the host key (the wrap key is elsewhere). A stolen whole-machine image in `file` mode does yield it (the wrap key is on the same machine). In `passphrase` mode it costs one Argon2id evaluation (m = 256 MiB, t = 3) per passphrase guess. A running process with root can read process memory. Documented as threat model L11.

### 15.5 Using the host key

- The server's host component loads wraps addressed to its `key_id` for the epochs of public channels, unwraps class keys with the host private key, derives `mk_c` for a message, decrypts only the class it is authorised for, and passes the plaintext to the specific feature. A feature never gets a key class it does not need.
- `push_text`: builds a preview `{channel_id, msg_id, title, body ≤ 140 chars}` and HPKE-seals it to each recipient device's `push_key` (17.3). The relay and the push services see only ciphertext. It is sent only to devices that registered `push_decrypt = true`.
- `search`: indexes tokens in an index encrypted at rest (15.4). A query is sent over the session; the server returns message ids and the client decrypts and checks them. The query text reaches the server.
- `scan`: decrypts `ct_f`, gets `file_key`, decrypts the blob in a sandboxed scanner, discards plaintext. It stores a **HostRecord** `{msg_id, file_id, verdict, scanner, at}` AEAD-sealed under `K_file`'s per-message key. Clients display the verdict as "Checked by the server (advisory)" and never treat "clean" as a promise.
- `transcode`: writes a derived blob under a fresh key; stores a `HostRecord` carrying `{derived_blob_id, key, mime, w, h}` sealed under the file class. Clients prefer a derivative when present.
- `link_preview`: decrypts `ct_u`, fetches each URL with the existing SSRF protections, builds `{url, title, desc}`, seals it under the U class as a `HostRecord`. Clients label it "Preview fetched by the server".
- `HostRecord = { msg_id, kind, host_key_id, nonce, ct }`, `ct = AEAD(mk_c, nonce, …, aad = H("hc/v1/hostrec", server_id, channel_id, msg_id, kind))`. Not signed by any member, so a hostile server can forge them; the UI labelling reflects that, and the content is never trusted for anything but display.

### 15.6 Rotation and revocation

- **Disable a feature.** `features_set` with the feature off. Every public channel's next epoch (9.3: trigger `feature_change`) lists the reduced `host.classes` and carries no wrap for a class no longer needed. If no feature remains, `host` is `null`, the `features_set` entry sets `host_key: null`, and the server destroys the host private key file, its in-memory copy and every feature-derived at-rest key and artifact (index, derivatives, caches), and drops the stored wraps addressed to it.
- **Rotate the host key.** `features_set` with the same features and a new `{key_id, pub}`. New epochs wrap to the new key; the old key is destroyed.
- **Compromise.** The owner uses "Turn everything off" (one disable entry plus rotation). It cannot take back what the host already could read.
- **What this cannot do.** The host keeps whatever it already decrypted or stored in plaintext, and nothing client-side can prove the server deleted a key. Turning a feature off guarantees that content encrypted after the change is unreadable to the host; it does not erase the past. Stated in the Threat model (L1, L11).

### 15.7 Notice to members

Clients render system notices **from the verified log**, never from server messages:

- On seeing `features_set` that changes the set, every affected channel shows a non-dismissible inline notice at the log position, and the server and channel levels change (SECURITY-LEVELS). Copy: *"The server owner turned on <feature>. The server can now read <what> in public channels."* On disable: *"The server owner turned off <feature>. New messages are no longer readable by the server."*
- A client that was offline sees the notices when it syncs the log; the level in its UI never lags the verified log.
- With push on, the server may wake devices with a content-free "Server settings changed" notice. This is a courtesy; the log is the notice.

### 15.8 How a client verifies the feature set in force

1. The feature set shown in the UI is computed from the verified log: the latest `features_set` entry (or none, meaning all off).
2. The server API may also return a feature status. It is advisory. If it differs from the log's, the client shows the log's state and flags "Server reports something different" (level "Not verified").
3. A client adds host wraps to a header only when the log says the feature is on, and only for `host.key_id` and `pub` from the log entry. A reader rejects a header whose `host` field differs from what the log at its `log_seq` authorises (9.4 rule 3). A header that carries a host wrap for classes not on in the log is invalid for everyone.
4. Therefore a server that is not holding the owner's signing key cannot make an honest client give the host anything. It can only (a) hide a real `features_set` entry from a client (detected as a stale head, 3.5), (b) replay an old entry (rejected: `seq` and `prev` chain), (c) ask a **malicious member** to hand it keys (that is the malicious-member threat, A6).
5. The server cannot add host access to *old* epochs: it would need someone to wrap those epochs' class keys to it, and honest clients only do so under a header they authored (new epoch).
6. Not verifiable by a client: whether the server really deleted keys and artifacts after disable. The owner is trusted to run the server honestly; the label never says otherwise.

## 16. Bots

### 16.1 Identity and enrolment

A bot is an account with its own `RS_bot`, generated **on the bot host** (the machine running the Chord runner), never on an admin's device and never on the server unless the host chooses to run both on one machine. It has `AccountPub`, `account_id`, a device key and a device certificate, and a role `bot` in the log.

1. The runner generates `RS_bot` and prints `bot_pub` fingerprint and a 6-word enrolment code `H("hc/v1/sas", "bot", AccountPub)` on its console.
2. The server stores the runner's pending enrolment. An admin's client lists it and asks the admin to type the 6 words from the runner's console (same check as 5.4; this stops a hostile server from substituting a key).
3. The admin signs `bot_add` (3.3 kind 10). The bot is now a server member with role `bot`, in no channels.
4. Per channel: an admin signs `bot_channel_add { bot_id, channel_id, history }` for a public channel (a private channel needs its creator). The default `history` is `from_now`. The next epoch of that channel lists the bot in `recipients` (class 0 wrap to the bot's `ak_dh`).

### 16.2 What a bot can do and not do

Can: read all content (and in calls, media) of the channels it was added to, from the epoch that lists it (or all history if `full`), sign messages as itself, join calls of those channels as a participant with `sender_key`.

Cannot: read any channel it was not added to; read DMs or group DMs (bots can never be added there: no `channel_member_add` kind for DMs accepts a bot); sign any log entry except its own `profile_set`; approve devices, join requests or invites; change features; add other members or bots.

Bots appear in the member list with a "Bot" tag. Steve's configured chat endpoint and speech endpoint are shown to members in the channel's security details: anything Steve reads may be sent to them (SECURITY-LEVELS 6).

### 16.3 Storage of bot keys

`RS_bot`, epoch keys it was granted, and its device key are stored in the runner's data directory encrypted with AEAD under `KDF(BWK, "host-at-rest" ‖ "bot")` where `BWK` is a bot wrap key supplied the same way as `WK` (separate file, `0400`, outside the data and backup paths; passphrase mode optional). The runner keeps epoch keys only for channels it is in.

### 16.4 Removal and theft

- Removing a bot from a channel rotates that channel's epoch; the bot (or whoever has its keys) can read nothing new there.
- If the bot host is compromised: the attacker reads every channel the bot is in, past (for epochs the bot holds) and future (until the admin removes the bot and the epoch rotates), and can post as the bot. They cannot read other channels, change membership or features, or read DMs. The remedy is `member_remove` on the bot's id (rotates every channel it was in) and re-enrolment with a new `RS_bot`.

### 16.5 Chords that are not bots

Gimme and Shared Browser do not read chat and do not hold channel keys. Their requests (search text, Plex requests, VM traffic) are visible to the server and the services behind it. Shared Browser sign-ins are visible to the host that runs the VM. These are labelled in their panels; they do not change a channel's security level (SECURITY-LEVELS 9).

## 17. Push notifications and the relay

### 17.1 Registration

1. The device registers its OS push token **directly with the relay** (operated by Maple Avenue Labs): `POST relay/v1/register { platform, token, app_id }` → `{alias}` (128-bit random). The alias is created per (device, server): the device passes the server's `server_id` so the relay can bind it.
2. The device sends `{alias, push_key_pub, push_decrypt: bool}` to its server (`POST /v2/push`).
3. The server stores `{device_id, alias, push_key_pub, push_decrypt}`. It never sees the OS token. Two servers that share a user get different aliases for the same device and cannot link the user by token.

### 17.2 Content-free default (D2)

The server sends `POST relay/v1/push { server_id, alias, collapse_id, payload }` authenticated by a server key registered with the relay. The default payload is `{"t":"wake"}` plus a fixed generic alert string ("New activity"). It contains no channel, no sender, no text, no mention flag. The relay maps `alias → token` and calls APNs or FCM. It rejects an alias whose bound `server_id` is not the caller's. A server registers its relay key by answering a challenge the relay sends to the server's `origin_hint`; the details belong in the push-relay document (`docs/PUSH.md`, to be revised).

For mentions-only users the server uses the cleartext `mentions` field (10.1, 19.1) to decide whether to send; the payload is identical, but the *existence* of the push reveals a mention to the relay and to APNs/FCM. Stated in 19.2.

Private channels, DMs and group DMs are always content-free.

### 17.3 Sealed text (only with `push_text`)

For each recipient device with `push_decrypt = true`: `payload = {"t":"msg", "s": HPKE(push_key_pub, info = H("hc/v1/push-seal", alias, msg_id), plaintext = CBOR{channel_id, msg_id, title, body≤140})}` ≤ 3 KiB. The app's notification extension (iOS) or background handler (Android) decrypts and shows it. The relay, APNs and FCM see only the ciphertext. Plaintext in the push payload is never allowed. If a platform cannot decrypt, it receives content-free pushes. If no platform at launch can decrypt, the `push_text` feature is not offered. (DECISIONS item 16.)

### 17.4 What the relay observes

See 19.3.

## 18. Rate limits

The current limiter (`AppState::limited` in `server/src/lib.rs`) uses one global counter per route per minute held in memory. One attacker can exhaust it and lock out everybody, and it resets on restart. v1 requires:

- Counters stored in SQLite so a restart does not reset them.
- Source address taken from `X-Forwarded-For` only from a configured trusted proxy; IPv6 sources are bucketed by /64.
- Every route has a per-source limit and a per-subject limit (username, account, request id) and a global ceiling. Hitting a limit returns 429 with `Retry-After`, and the response time does not depend on whether the subject exists.

| Operation | Limit |
|---|---|
| OPAQUE `login_start` | 20 / min / source; 600 / min global |
| OPAQUE `login_finish` failure, per username | 5 consecutive failures → lock the **password path** for that username for 10 min, doubling on each further 5 failures, to a maximum of 24 h; counter decays after 24 h with no failure. Registered devices keep working: they use the signed session path, not the password path. |
| Device-approval requests | 1 outstanding per account; 3 per day; 24 h cooldown after a deny |
| Pending-code attempts on the approver | 5 wrong codes → request cancelled |
| `join` with invite | 5 / hour / source; 10 failed invite ids / hour / source |
| `join-requests` | 5 / hour / source; 20 pending per server; 1 per username |
| `replace-requests`, `recover` | 5 / hour / source; 3 / day / username |
| Claim (`/v2/claim`) | 10 wrong tokens then locked until restart |
| Friend requests | 20 / day / account to non-friends; 5 pending per recipient |
| Typing events | 1 / 3 s / channel / device |
| Messages | 30 / 10 s / device (burst 10); 20 attachments / message |
| Blob upload | per-account byte quota, configurable; 429 beyond it |
| `profile_set` | 5 / hour |
| Session challenges | 30 / min / device |

Online guessing against one username through the password path is therefore at most 5 guesses per 10 minutes at first and 5 guesses per 24 hours after a long run of failures. (The password lock never blocks an already-registered device, so it cannot be used to lock the owner out of their own devices.)

## 19. What the server and the push relay can observe

### 19.1 Server (the host)

**Sees in plaintext:** usernames and display names; every account's public keys; the full signed log (membership, roles, bans, channel ids and kinds, bot list, feature set, invites); which channels exist; each member's channel membership (public channels: everyone; private channels: the list in the log); device list with device names, creation and last-seen times; IP addresses and user agents; when each account is online; message metadata: channel, epoch, sender account and device, `sender_seq`, send time, size of each ciphertext class, which messages are edits and deletes and what they target, **who was @mentioned** (the `mentions` field is clear by design, so mentions-only notifications can work); who sends mail (friend requests) to whom, and when; which friends talk to which (DM membership, volumes and times); attachment sizes and upload times; typing events and their timing; call room names, participants, durations, track types, rates; push aliases; the activity of Chords (Plex, Shared Browser).

**Cannot see (default configuration):** message text, edits, reactions, pins, replies, channel names and topics (they are messages), file names and contents, thumbnails, link URLs, call media, friend request text, read state, notification settings, friend lists, petnames, passwords, `RS`, any private key, the recovery phrase.

**Can do beyond observing:** drop, delay, reorder or withhold anything; refuse service; show different members different data (detected only through cross-references, 3.5); serve a malicious web client (20).

**With host features on (public channels only):** the classes in 15.2 for epochs created after the `features_set` entry.

### 19.2 Push relay and the push services

Sees for each push: the server's identity, the alias, the target platform, time, size, collapse id; and the OS token it was given at registration. It also sees how often a given server pushes to a given alias, which reveals when that person is active or mentioned. APNs and FCM see the token, the time, the size, the app id and the payload bytes (content-free text, or ciphertext when sealed text is on). Neither sees usernames, channels, senders or message text. The relay cannot link a person across two servers by token (aliases differ), but the relay itself holds all tokens and could link them if it tried (it stores `alias → token`). Maple Avenue Labs commits not to, and that is a promise, not a mechanism.

### 19.3 LiveKit (SFU and TURN)

Covered in 12.4. It is part of the server for trust purposes; the SFU operator is the host.

## 20. Web client

### 20.1 What is served

The server serves the web client as static files with a manifest:

```
Manifest = SignedObject under the project's release key, label "hc/v1/release-manifest"
payload { 1 v:1, 2 version:uint (monotonic), 3 released_at, 4 files:[{path, sha256}], 5 wasm_sha256, 6 min_version }
```

The release key is an Ed25519 key held by the project (offline). Its public half is published in the repository, on the release page, and embedded in the desktop and mobile apps. The Maple Avenue Labs release process signs the manifest for every release; server operators serve the files and manifest unchanged.

### 20.2 Hardening

- CSP `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; img-src 'self' blob: data:; media-src 'self' blob:; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`; no inline scripts or styles; Trusted Types required; SRI attributes on every script; no third-party origins, analytics or fonts; `Cross-Origin-Opener-Policy: same-origin`; `Referrer-Policy: no-referrer`.
- All crypto in a dedicated Worker; `RS` never in the main thread (1.3).
- A service worker caches the signed bundle. On each navigation it fetches the manifest and signature, verifies the signature with the release public key **baked into the service worker file**, rejects a `version` lower than the one it has stored (rollback), verifies each file's hash before caching, and switches to the new bundle atomically. If verification fails it keeps the old bundle and shows "This server's web app failed verification".
- An audit command (part of the desktop app and a small CLI): `housecall verify-web <url>` fetches the served bundle and manifest and verifies it against the release key independently of any browser state. Owners are told to run it after every update, and members can run it at any time.

### 20.3 The limit, stated plainly

The first time a browser loads the web client, the code comes from the host. If the host is malicious at that moment, it can serve code that steals the password and `RS`; nothing in the browser can detect this. After the first load, the service worker checks later bundles against the release key, but **the service worker script itself is also fetched from the host** and the browser replaces it when the file changes: a malicious host can ship a replacement service worker that skips verification. The signed bundle therefore gives detection (through `verify-web`, and through the page showing the manifest hash that the project publishes), not prevention. The security level on web is capped for this reason (SECURITY-LEVELS 3). Desktop and mobile apps are the recommended clients: their code comes from signed GitHub releases and never from the server.

The web client must also show, on its first screen, the installed manifest version and a link to the verification instructions.

## 23. Negative tests an implementation must pass

Each must fail in the stated way. They belong in the implementation's test suite, separate from the independent attack run in `CRACK-PLAN.md`.

**Encoding and signatures**
1. A signed object with a flipped bit in the payload fails verification.
2. A signed object whose payload re-encodes to different bytes (non-deterministic CBOR) is rejected before signature verification.
3. A signature from the right key but a different label fails.
4. A non-canonical Ed25519 signature (S ≥ L) and a small-order public key are rejected.
5. Duplicate map keys, indefinite lengths, trailing bytes and an unknown `v` are rejected.

**Log and membership**
6. An entry signed by a non-admin for a kind that needs admin is invalid.
7. An admin trying `features_set`, `role_set`, or removing the owner or another admin is invalid.
8. An entry with a wrong `prev`, a repeated `seq`, or a skipped `seq` is invalid.
9. A `member_add` whose `pop` is signed by a different key is invalid.
10. A `member_join` using an invite already used by an earlier entry, a revoked invite, or one whose issuer is no longer admin is invalid.
11. A `member_join` with `invite_pop` made by a different key than `token_pub` is invalid.
12. A server that returns the log with the last entry removed (rollback) is detected after the client has stored a higher head.
13. Two different entries with the same `seq` (fork) are flagged once both are seen.
14. An admin who is not the creator cannot add themselves to a private channel.
15. A bot-signed entry (other than its own `profile_set`) is invalid.

**Server identity**
16. A server whose entry 0 hash differs from the pin is refused.
17. An invite link whose `s` does not match the server's entry 0 is refused.

**Password, devices, sessions**
18. A login with a wrong password fails at finish and leaks no information beyond failure; unknown and known usernames are indistinguishable by content and (within noise) by timing.
19. An OPAQUE login with a different `server_id` or device key in the context fails.
20. A blob decrypted with the right export key but whose `account_pub` does not match the log is rejected.
21. A blob under a different `server_id`, username or `version` in the AAD fails.
22. A pending device cannot call anything except its own pending request.
23. An approval signed by a revoked device, by a device of another account, or after expiry is rejected. An approval where the typed code does not match is not sent.
24. A session signature made for another `server_id` or `origin` fails.
25. A reused or expired challenge nonce fails.
26. A revoked device's token stops working immediately, including open sockets.
27. 5 failed password logins lock the password path; a registered device can still open a session.
28. A weak password (< 12 bytes or zxcvbn < 3) is rejected on the client; the server also rejects anything under 12 bytes.

**Epochs and wraps**
29. A header with a recipient not in the expected set (ghost), or missing one that is expected, is rejected.
30. A header whose author is not a member at `log_seq`, or whose signature fails, is rejected.
31. A header with `epoch` not `prev+1`, a wrong `prev_hash`, or a lower epoch than stored (rollback) is rejected.
32. A header with a `host` entry the log does not authorise (feature off, wrong `key_id`, extra class, private channel or DM) is rejected.
33. A wrap with a different key than the check in the header is rejected.
34. A wrap whose `header_hash` was altered fails to decrypt.
35. A client holding epoch `n` refuses to send after a verified removal until epoch `n+1` exists; with the server refusing `n+1`, sending fails and does not fall back to `n`.
36. A new device shown only an epoch from before the last removal refuses to send.
37. A history grant for a `from_now` member is rejected.

**Messages and attachments**
38. A message with a wrong channel id, epoch, `msg_id` or sender in the AAD fails to decrypt.
39. A message signed by a non-member, or by a member removed at `log_seq`, is dropped.
40. A replayed message (same `msg_id`) is dropped; the same `msg_id` with different bytes is flagged.
41. A message with a lower or repeated `sender_seq` is dropped; a gap is surfaced.
42. A live message to an epoch older than the adopted one is dropped.
43. An edit or delete from someone other than the author (and not an admin in the channel) is ignored.
44. A message whose `log_head8` contradicts the reader's verified hash flags a fork.
45. A file blob with a flipped bit, a swapped chunk, a missing last chunk or an appended chunk fails; a blob decrypted with another `file_id` fails.
46. A per-message key for message A does not decrypt message B.

**Calls**
47. A participant with no key sees only ciphertext; a participant with a key from a previous generation cannot decode frames sent after the re-key.
48. After a member is removed, frames sent more than 10 seconds after the re-key are undecodable by them.
49. A LiveKit identity that is not a log member is shown as unverified.

**DMs, friends, bots**
50. A DM header with a third recipient or a host entry is rejected.
51. A friend request signed by a different key than the claimed `from`, or addressed to another account, is rejected.
52. A request using a friend's display name with a different `account_id` is flagged and cannot be auto-accepted.
53. A bot cannot be added to a DM or group DM; a bot cannot read a channel it was not added to (no wrap).
54. A group DM add by anyone other than the creator is invalid.

**Host key and features**
55. With all features off, no `HostKeyFile` exists and no header contains `host`.
56. No environment variable, config key or API call enables a feature without a `features_set` entry signed by the owner.
57. Enabling a feature produces headers with only the needed classes; the host cannot decrypt `ct_t` with an `F`-only wrap and cannot derive `K_call`.
58. After disabling, new epochs carry no host wrap and the key file and derived artifacts are gone.
59. The host key file does not decrypt without `WK`; no plaintext host key, class key or `EK` appears in the database, WAL, logs, crash dumps or swap-backed config in a scan after a test run.
60. A locked host (passphrase mode, no passphrase) serves chat normally and degrades features as specified.

**Web client**
61. A bundle with a hash not in the manifest, a manifest with a bad signature, or a lower `version` is refused by the service worker.
62. No inline script or third-party origin is accepted by the CSP; the page passes the header checks.

**Rate limits**
63. Limits in section 18 hold across a process restart; one source cannot exhaust another source's budget; an invalid request does not reveal whether a username exists.

## 24. Open spikes

These must be settled before the matching code is written (Task 0.6 and the LiveKit spike). Each has a stated fallback.

1. `opaque-ke`: version that tracks RFC 9807; compiles to WASM; Argon2id at m = 64 MiB, t = 3, p = 1 time in desktop Chrome, Safari, and a mid-range Android phone. Fallback if too slow on mobile web: keep the parameters and show a progress indicator (the cost is the defence); do not lower them without a note in DECISIONS.
2. HPKE crate: `hpke` vs `hpke-rs`/`libcrux`: WASM compiles, deterministic-ephemeral test hooks for vectors.
3. `chacha20poly1305` with `aead::stream` compiles to WASM; confirm the XChaCha20 STREAM nonce prefix is 19 bytes.
4. Strict CBOR: choose between `ciborium` and `minicbor` and write the strict pre-check.
5. `zxcvbn` size and WASM compile.
6. LiveKit per-participant keys with `BaseKeyProvider`: five webviews, key-index rotation, 30 participants, and the Rust SDK for the Steve DJ.
7. iOS notification service extension that can decrypt sealed pushes (17.3). If not shipped, `push_text` stays unavailable at launch.
8. Platform secure storage for `RS` on Linux without a keyring running (headless desktop sessions).
