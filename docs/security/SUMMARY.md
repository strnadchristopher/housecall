# Housecall security: summary for the product owner

Status for 0.4.0: the two contracts below are written and have test vectors generated by running code. The code is not built yet. Before the code starts, an attacker session reviews the contracts on paper. After the build, a fresh session attacks the running system (`ATTACK-RUN-0.4.0.md`). No human or outside firm has audited any of it. Until the attack run passes, nothing here should be called "secure" in public.

What 0.4.0 builds:

- **`DM-V1.md`**: end-to-end encryption for one-to-one DMs.
- **`LINK-V1.md`**: QR login and device linking, which also carries your keys to the new device.
- Vectors in `client/tests/vectors/` from `node client/scripts/security-vectors.mjs`.

`PROTOCOL.md`, `CRACK-PLAN.md`, `REVIEW.md` and `THREAT-MODEL.md` in this folder describe a much larger future design (encrypted channels and calls, signed member lists, OPAQUE passwords). **None of that is built or planned for 0.4.0.** It is kept for later.

## What members can rely on in 0.4.0 (once built as written)

- **One-to-one DMs between two people using the app are readable only by those two people.** The host stores scrambled text and files and cannot read them. That holds once both people have keys and each app has pinned the other's key.
- **The host cannot forge a DM or change who sent it.**
- **The host cannot quietly switch a DM back to readable text.** The app refuses once it has seen the other person's key, and the server refuses unencrypted text in a DM where both people have keys.
- **A password is never a key.** Someone who steals your password cannot read your encrypted DMs.
- **A recovery key (24 words) gets your keys back** on a new device, together with being able to log in. The host cannot open it.
- **Logging in with a QR code needs your approval** on a device where you are already logged in, after checking that both screens show the same two-digit number. A photo of the code is not enough.
- **The label never overstates.** "End-to-end encrypted" shows only in a one-to-one DM, in the app (not the browser), with both people's keys in place and the other person's key pinned.

## What the host can see

| | Host can see |
|---|---|
| Channels, voice channels, group DMs | Everything |
| Encrypted one-to-one DMs | Who talks to whom, when, how often, roughly how much, reactions, replies, pins, read and typing state. Not what is said. |
| Files in encrypted DMs | Size and time only |
| Calls, including DM calls | Could listen: calls go through the host's server and are not end-to-end encrypted |
| The web version | Everything that browser user can read, because the host serves the page |

## What is not protected

- **No forward secrecy.** Anyone who later gets one person's key (a stolen unlocked phone, or recovery words plus account access) can read all of that person's encrypted DMs, past and future, until they reset.
- **Trust on first use.** The first time a device sees someone's key, a hostile host could substitute its own. Comparing safety numbers detects it. A device restored from recovery words, and every browser session, starts from scratch.
- **Group DMs, channels and calls** are not end-to-end encrypted.
- **The web version** trusts the host. It may read encrypted DMs (keys kept in memory only) but is labelled "Encrypted in browser", never "End-to-end encrypted".
- **A password thief can reset your keys.** They still cannot read old messages, but everyone you DM sees "security key changed" and has to accept it, and your own devices raise an alarm.
- **Same identity on every host.** You have one recovery key, so two hosts that compare notes can tell it is the same person.
- **The host can drop, delay, reorder or replay messages**, and can show an older version of an edited message.
- **What the other person keeps.** They can copy or screenshot anything you send.

## What has not been tested

- **No code exists yet.** The vectors prove the formats are implementable with the chosen libraries (`@noble/curves`, `@noble/ciphers`, `@noble/hashes`, `@scure/bip39`), not that the app uses them correctly.
- **The attack run has not happened.**
- **No outside audit.** The explainer says "attack-tested by us, not audited by an outside firm" once the attack run passes, and not before.
