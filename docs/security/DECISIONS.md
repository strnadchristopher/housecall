# Security decisions

For each item in the plan's security baseline (`PLAN.md` 3.2) and its consequences table (3.3): **kept**, **changed** or **rejected**, and why. Then the decisions this spec added, the alternatives it rejected, the points that need Christopher's confirmation, and the places where it departs from the wording of `DECISIONS-1111.md`.

Numbers are cited from `PROTOCOL.md` and `THREAT-MODEL.md`.

## A. The baseline in plan 3.2

| # | Baseline item | Verdict | What and why |
|---|---|---|---|
| 1 | Account root key recovered from the password-protected blob; each device has its own key certified by the root; sessions are signed challenge-response by the device key | **Changed** | Kept: one account root secret `RS` recovered from the blob; a device key and a certificate; sessions by signed challenge with short-lived tokens (PROTOCOL 1, 6). Changed: **messages and log entries are signed by the account key, not the device key.** Every device holds `RS` (the fixed requirement is that any device with the account key reads history), so a device signature would add certificate checking for every message and no security: a thief who has the device has `RS` too. Device keys remain for session authentication and per-device server-side revocation only. Added: the account key is split by HKDF into a signing key, a DH key and a state key from one 32-byte `RS`, so the recovery phrase is one value (PROTOCOL 1.1, 8.1). |
| 2 | OPAQUE for the password proof; its export key (memory-hard KSF) encrypts the blob; each server stores a copy | **Kept** | OPAQUE (RFC 9807) is the standard answer to "prove the password without sending it". Kept per server, with `server_id` as the OPAQUE server identity and the device key in the login context. Details added: Argon2id m = 64 MiB, t = 3, p = 1 (plan Task 0.6 numbers; the spike may raise them); NFKC normalisation; a strength rule; the server's OPAQUE secret wrapped by a key that is not on the data volume (PROTOCOL 2.5), so a stolen volume or backup alone does not enable offline guessing. Stated limit, not hidden: a server with its own secret can still guess offline (L2), and because `RS` is the same on every server, one weak password endangers every server (L16). |
| 3 | Membership is a log of admin-signed entries that clients verify before wrapping keys to anyone | **Kept, extended** | The log is the answer to the ghost-member problem. Extended to carry: invites as signed certificates, roles, bans, bot membership, key replacement, and the host-assisted feature set (so a server cannot enable host access without the owner's signature), and a mini-log for group DMs (PROTOCOL 3, 13.4). Rollback and fork detection added: every message and header carries the author's log position and a hash prefix (PROTOCOL 3.5). |
| 4 | Per-channel epoch keys wrapped to each member's account key; rotation on removal; invite decides whether earlier epochs are wrapped | **Changed** | Kept: epochs, per-member wraps, rotation on removal, history chosen by the admin per invite. Changed: (a) wraps are HPKE with the header hash in `info` and `aad`, and a key check inside the **signed epoch header**, so a server cannot substitute a key; (b) the signed header lists the **exact** recipient set, and readers reject any superset or subset, which is what stops a ghost recipient (PROTOCOL 9.4); (c) the epoch key derives separate **class keys** for text, files and URLs, so a host feature can be given exactly the class it needs and nothing more (PROTOCOL 9.1, 15); (d) rotation is eager for the device that signs the change and **mandatory before the next send** for everyone, so no client ever encrypts under an epoch that still lists a removed member, even if the server refuses the new epoch (PROTOCOL 9.3); (e) "from now on" is implemented as a rotation at join, and "full history" as signed history grants from existing members (PROTOCOL 9.6). |
| 5 | Messages: AEAD with channel, epoch, sender device and message id as associated data; signed by the sender device | **Changed** | AEAD with identity in the AAD is kept. Changed: signature by the account key (see item 1); XChaCha20-Poly1305 with random 192-bit nonces, so many devices write under one epoch key with no nonce coordination and no message-count limit; a **per-message key** derived from the class key so one message can be disclosed in a report without exposing the epoch (PROTOCOL 10.2, 10.8); padding to 256 bytes; a per-device `sender_seq` so a dropped, replayed or reordered message from one sender is visible (PROTOCOL 10.6); reactions, edits, pins and channel names are also messages so the server cannot see them. |
| 6 | Attachments: random per-file key carried in the message; chunked AEAD reusing the `crates/media` chunk format with a client-held key | **Changed** | Kept: random per-file key carried inside the encrypted message, chunked. Changed: the existing `crates/media` format (AES-GCM with a random nonce stored per chunk, AAD of id, offset and length, and a server-held key) is not reused as is. The new format is the STREAM construction over XChaCha20-Poly1305 from the RustCrypto `aead` crate, which detects truncation and extension with a last-chunk flag, and allows random-access decryption for media seeking without storing nonces (PROTOCOL 11). The file key travels in the **file class** of the message, so a host that only reads text cannot decrypt files. The crate's range and storage code can be adapted; its server-held key becomes optional at-rest encryption of ciphertext. |
| 7 | Calls: LiveKit frame encryption keyed from the channel epoch key and call id; re-keyed on membership change | **Kept, specified** | Call key `ck = HKDF(EK_n, call_id, channel, n, generation)`, per-participant sender keys derived from it, re-key on every epoch change, 10-second overlap (PROTOCOL 12). The host never has `EK_n`, so no host feature can ever read a call. Not provided and stated: forward secrecy inside a call, sender authentication among members, hiding speaker activity from the SFU (L14). Needs a spike: LiveKit per-participant key mode in all five webviews and the Rust SDK for Steve. |
| 8 | Server identity key; fingerprint inside invite links; clients pin it and warn on change | **Changed** | There is no separate server key. A server's identity is the **hash of its genesis log entry**, signed by the owner (PROTOCOL 3.5). The invite link carries it, clients pin it, and it also fixes the owner key. A second key would add nothing: TLS already authenticates the address, and what a member needs to know is "this is the server whose signed history I joined", which the genesis hash already says, and it survives a change of domain. A new device pins from the account's encrypted state or, on first contact, from TLS and OPAQUE (L7). |
| 9 | Web: strict CSP, no third-party origins, service worker verifies each bundle against the project's release signature after first load | **Kept, with limits stated** | All kept, plus Trusted Types, SRI, `wasm-unsafe-eval` (needed for the crypto WASM; the current CSP in `server/src/lib.rs` lacks it), crypto in a Worker so `RS` is never in the main thread, a monotonic manifest version against rollback, and a `verify-web` command that checks a served bundle outside any browser state (PROTOCOL 20). Stated plainly: after the first load the **service worker itself is fetched from the host**, so a hostile host can replace it. The signed bundle gives no prevention, and detection only of a swap served to everyone: a host can show `verify-web` a clean bundle and serve altered code to one user (L12; review finding 12). Because of this the web client's label is capped at level 3 "Host serves this app" (SECURITY-LEVELS 3). Native apps are the recommended clients. |

## B. Consequences in plan 3.3 and D1/D2

`DECISIONS-1111.md` D1 replaces "No server-trusted mode" and plan 3.3. The table gives the end state.

| Existing feature | Plan 3.3 said | Verdict | End state |
|---|---|---|---|
| ClamAV scanning | Removed | **Changed** (by D1) | Off by default. Host feature `scan`: the host holds the **file class key** for public channels from the enable point on, scans, and stores an advisory verdict. The client never auto-opens files either way and never treats "clean" as a promise. Level "Server sees files". |
| Server transcoding and thumbnails | Removed for uploads | **Changed** (by D1) | Clients make thumbnails and previews before encrypting. Host feature `transcode` (file class) lets the host write derived files. `transcode.rs` stays for Plex streams. |
| Server link previews (`embeds.rs`) | Sender's client fetches | **Changed** (by D1) | Default: the sender's client fetches, with a setting to turn it off. Host feature `link_preview`: the sender's client puts the URLs in a **URL class** field and the host fetches. Only URLs are exposed to the host, not text or files. |
| Server search | Client-side index | **Changed** (by D1) | Default: per-device index. Host feature `search` (text class): the host indexes in an index encrypted at rest. Queries reach the host. |
| Push with content | Content-free | **Kept, with D2** | Default content-free through the relay. Host feature `push_text`: a preview **sealed to each device's push key** so the relay and Apple/Google see only ciphertext (PROTOCOL 17.3). If no platform can decrypt at launch, the feature is not offered (see item 16). |
| Reports with server-read content | Reporter attaches a decrypted copy | **Changed** | A copy typed by the reporter cannot be checked. The report carries the sender's signed message and the **per-message key**; the admin verifies and decrypts it themselves (PROTOCOL 10.8). |
| Passkeys, email invites, password login | Removed | **Kept** | Removed. The old routes are deleted, not left behind a flag (CRACK-PLAN C04 step 2). |
| Multi-server table (`servers.rs`) | Removed | **Kept** | One deployment is one server. Cross-server identity is `account_id`. |

## C. Decisions this spec added

Numbering continues so other documents can cite "DECISIONS item N".

10. **One account secret across servers** (plan: one identity across servers). Kept. Cost: L16. **Rejected alternative:** a separate key per server with cross-signatures. It isolates a breach to one server only if the password also differs, and users reuse one password, so it buys little for the complexity.
11. **No MLS.** Rejected, though it gives forward secrecy and post-compromise security. The fixed requirement that any device reads all given history forces long-lived keys anyway, MLS's tree operations are heavy for web WASM and for a 30-person call server design, and the `openmls` crate's maturity under WASM is a risk. Revisit if forward secrecy becomes a requirement.
12. **No hardware-bound device keys and no per-device decryption keys.** Rejected. Secure Enclave and StrongBox do not offer Ed25519, and per-device decryption keys would mean wrapping history per device and re-wrapping on device change. Consequence: device revocation is not cryptographic (L5). The remedy is "Secure my account" (PROTOCOL 8.4), a key replacement approved by an admin.
13. **No "secret key" in addition to the password** (the 1Password design). Rejected. It would make device approval cryptographic and stop the offline attack, but it breaks "password alone works when no other device exists" and adds something to write down at signup, against D6. Instead: server-enforced approval with a code, plus a recovery phrase, plus a strength rule. L2 and L3 are the price.
14. **Seven-day auto-approval of a device request** (new). Plan: "password alone works only when no other device exists". Taken literally, a user whose only device was lost still has it registered, has no phrase, and is locked out forever. The delay lets them in after seven days with daily notices on every other device and a deny button. Flag for Christopher: it can be lengthened, or removed if lockout is preferred over this risk (A5a). Changed by the review: the auto-approval fires only if no active device opened a session during the seven days, and a denial puts a cooldown on the requesting source and device key, not on the account (PROTOCOL 7.3). The recovery phrase now follows the same rules when the account still has an active device (PROTOCOL 8.2), so the phrase is immediate only when no device is active (see E).
15. **Host features cover public channels only** (new narrowing of D1). Private channels, DMs and group DMs are never host-readable, and clients reject any header that says otherwise. Why: plan 1 says admins cannot read private channels they are not in, and "owner turns on push text" should not let the host read a private channel. Cost: no notification text for DMs or private channels even when the owner turns it on. Flag for Christopher.
16. **Push text is sealed to the device, never plaintext through the relay** (D2 left this open). Needs an iOS notification service extension and an Android background handler; plan assumption A5 said no extension. If no extension ships at launch, `push_text` is not offered. Flag: if Christopher wants push text at launch without the extension, the only way is plaintext through Maple Avenue Labs' relay and APNs/FCM, and the labels must say "Server and push services read messages". That is a different feature and needs its own decision.
17. **The host key exists only while a feature is on** (D1 says "each server has a host key"). Generated on the owner's request, published in the owner-signed entry, destroyed when the last feature goes off (PROTOCOL 15.3 to 15.6). Why: a key that does not exist cannot be stolen, and "stolen disk image" with all features off then yields nothing. Wording difference only; the behaviour in D1 (key holder for exactly what the feature needs; members told; turning off rotates keys) is implemented in full.
18. **At-rest wrap key `WK` outside the data volume** protects the host key, the OPAQUE secret, and every host-derived artifact. Default file mode (a root-owned file in a separate directory), hardened passphrase mode (Argon2id at 256 MiB), TPM sealing left to a later version. Honest result: protects against stolen data volumes and backups; does not protect against a stolen whole machine in default mode (a hosting provider's disk snapshot counts as one) or against root on the running machine (L11). In passphrase mode the passphrase is generated at install (8 BIP-39 words) rather than chosen by the operator, and a locked server refuses password sign-in and joining while registered devices keep working (review findings 18 and 23). The operator documentation must say where `WK` is and to back it up separately.
19. **Level ranking** (SECURITY-LEVELS 1): messages 1, files 2, links 3, web page 3, bot 1. Two judgment calls to confirm. A bot is level 1 because it reads everything in its channel, so a channel with Steve never shows full encryption; that is accurate, and the server-level view uses the label "Bots in some channels" so one bot does not read as the server reading messages. The web cap is level 3 because nothing is read by design but the host could change the page. Alternative: a separate "client trust" indicator instead of lowering the bar. Rejected because D1's rule is that the bar must never overstate.
20. **Invites are certificates plus a secret the server never sees** (plan: "an admin approves it, or an invite token does"). An admin signs an `InviteCert` containing a public key derived from a token seed that lives only in the link; the joiner proves possession by signing their join with that key (PROTOCOL 5.2). Effects: the admin need not be online; the server cannot substitute a joiner's key; single use is enforced by the log. Expiry is policy, not cryptography (no trusted clock). Invites are shared only as `housecall://` links or copyable text, never as an `https://` link to the server, because the host's page could read the secret (review finding 7).
21. **Tokenless joins need a six-word check** between requester and admin; there is no approve-without-check path (PROTOCOL 5.4). It costs the admin one phone call or message, which they need anyway to know who the stranger is. Six words (66 bits) because a hostile server could grind a four-word match in days. The code is computed from `server_id` and the requester's key only: an earlier draft included a server-chosen request id, which let a server grind a collision between two requests in about 2^33 hashes (review finding 1).
22. **The rate limiter is replaced.** The existing one (`AppState::limited`) is a single in-memory counter per route, so one source can lock out every user and a restart resets it. v1 requires persistent, per-subject, per-source limits, with registered devices unaffected by password-path lockout (PROTOCOL 18).
23. **@mentions are visible to the server.** A mentions-only notification setting needs the server to know who was mentioned. The alternative (push everything, decide on the device) means a push for every message to everyone, which wakes phones and tells the push services the activity level of the whole channel. Chosen: the mention list is clear metadata (L6, L20).
24. **Deterministic CBOR, and signatures over the exact bytes sent** (PROTOCOL 0.1). Rejected: JSON canonicalisation (several incompatible rules), and re-encoding before verifying (the classic source of signature bypass).
25. **No ownership transfer in v1.** The owner cannot leave or be replaced. A lost owner key with no phrase leaves a server that works but whose features can never change. Add transfer later as a two-signature entry.
26. **No metadata hiding.** Sealed sender, padding of timing, and cover traffic are not attempted. The host sees who talks to whom (L6). Stated rather than half-done.
27. **Library choices** (PROTOCOL 0.3). `opaque-ke` rather than SRP, a hand-made PAKE, or server-side Argon2 (which would send the password to the server). HPKE (RFC 9180) rather than a custom sealed box. XChaCha20-Poly1305 rather than AES-GCM for message and file encryption because random 192-bit nonces remove a whole class of mistakes with many writers; AES-GCM stays inside LiveKit where it is the SDK's choice. `ed25519-dalek` with strict verification. No crate or construction here is new; the combinations (export key → blob key; HPKE bound to a signed header) are small and spelled out for review.
28. **Passwords: 12 bytes and zxcvbn score ≥ 4** (changed from 3 by the review, finding 10). The arithmetic in CRACK-PLAN C09: score 3 means an estimated 10^8 guesses or more, about 116 core-days at 0.1 s per guess, but the right model is a GPU: each guess moves about 0.5 GB through memory, which puts one high-end GPU near 10^3 guesses per second (an estimate for C09 to measure), so score 3 falls in about a day and in minutes on a rented rack. Score 4 (about 10^10 guesses) costs about 100 times more. D6 (ease first) argued for 3; the spec now holds 4 because the guessing target is `RS`, the account on every server. Flag for Christopher (E): a score-4 password is roughly a four-word passphrase or 14 random characters, which makes sign-up harder. The alternative is to keep 3 and raise the Argon2 cost if the spike shows mobile can afford it.
29. **Calls re-key on epoch change only**, not on leave or timer. A leaver who remains a channel member can derive the key anyway (PROTOCOL 12.3).
30. **DMs and friends.** A DM is pinned to a home server both parties share; one thread per pair; a replaced key creates a new thread; group DMs have a creator-controlled mini-log and must sit on a server where everyone is present (PROTOCOL 13). Friend lists live in the encrypted account state, not on a server in readable form. Rejected: a global directory (needs a service and leaks the social graph).
31. **Password change updates every server the account is on, and requires the old password even from a signed-in device** (PROTOCOL 2.6). Servers that cannot be reached keep accepting the old password until they are reached; the UI says so.

## E. Needs Christopher's confirmation

1. Host features cover public channels only (item 15).
2. Seven-day auto-approval (item 14).
3. Push text only if a device-side decryption extension ships (item 16).
4. Bot is level 1; web is capped at level 3 (item 19).
5. Password rule is now score 4, up from 3 (item 28). This makes sign-up harder; say if you prefer score 3 with a higher Argon2 cost.
6. The host key exists only while features are on (item 17).
7. Web client label "Host serves this app" means web users never see "End-to-end encrypted" (item 19). Native clients do, unless someone else in the conversation uses the web version (then "Member on web app", level 3; review finding 11).

Added by the review of 2026-11-11 (each changes what users see or what the host may do):

8. The recovery phrase is immediate only when the account has no active device. With an active device (including a lost phone that is still registered) a recovery waits for approval or the seven-day period and tells every device (PROTOCOL 8.2). Alternative: keep it immediate and accept that a copy of `RS` on a stolen or revoked device can silently take the account and reset the password.
9. `push_text` now carries the member's signed message to the device, which decrypts and verifies it, so the host no longer needs to read the text for a notification when the message fits (PROTOCOL 15.5, 17.3). The feature still counts as a text feature (level "Server reads messages") in v1. Decide whether to drop the host's text access for `push_text` altogether.
10. Heads must be fresh (3.5 item 4): if nobody else on a server has made a log entry within 24 hours, clients sign automatic `checkpoint` entries; a client that still sees no fresh entry shows "Not verified" and pauses sending. Cost: a server where one person is the only active member is exempt, but a two-person server where the other person is away for a day relies on that person's app signing checkpoints.
11. An admin who is removed or demoted loses all authority; a private channel or group DM whose creator is removed is frozen (nobody can add or remove members) instead of passing to the owner, because passing it on would let an admin read a private channel (PROTOCOL 3.3 R1 to R3).
12. Files converted by the host (transcode) are shown only when the original cannot be played, and are labelled "Converted by the server" (PROTOCOL 15.5).

## F. One-page summary of what users will notice

- **Passwords and keys.** Users pick a username and a password on their device. The server never sees the password. Forgetting it with no recovery phrase and no other signed-in device means an admin must approve a fresh identity, and old direct-message history is gone.
- **New devices need an OK from an old one**, by typing a six-digit code. Someone who steals only a password cannot get in. If a user loses their only device they can get back in with the password or the recovery phrase after seven days; the phrase works immediately only if no device is still registered. If the user keeps using any device during that week, nobody is let in without approval.
- **Joining** by link needs no admin online. Joining by asking needs an admin to confirm six words read aloud.
- **History.** Admins choose per invite: full history or from now on.
- **Removal.** A removed person cannot read anything new. They keep what they already read.
- **Steve and other bots** can read the channels they are added to, and the label says so.
- **Host features** are off. When the owner turns one on, every member sees a notice and a lower level. Only public channels are affected. DMs and private channels never are.
- **Web version** shows a lower level than the apps, because the host serves the page, and conversations with a web user in them show a lower level to everyone in them.
- **No server-side scanning, transcoding, search or link previews** unless the owner turns them on.
- **Notifications** say "New activity" and nothing else unless the owner turns on text previews and the user's device can decrypt them.
- **Not provided:** forward secrecy for stored history, hiding who talks to whom from the host, or erasing what was already read or copied. The README says no human audit has happened.

## G. Code that this spec obliges the implementation to change

For the implementer's checklist; not a design.

- `server/src/lib.rs`: replace `AppState::limited` and `public_limit` (PROTOCOL 18); drop `X-Device-Key` and bearer-hash sessions for the challenge sessions in PROTOCOL 6; add `'wasm-unsafe-eval'` to the CSP; replace users, sessions, invites, members, messages tables with the v2 tables; remove the `/api/setup`, `/api/login`, `/api/invites/accept` routes.
- `server/src/passkeys.rs`, `server/src/servers.rs`: delete.
- `server/src/embeds.rs`, `server/src/transcode.rs`, `crates/media` scanner code, the `scanner` compose services: move behind the host features in PROTOCOL 15, or delete.
- `server/src/push.rs`: split into the content-free default and the sealed path (PROTOCOL 17).
- `server/src/voice.rs`, `crates/sfu`: replaced by LiveKit (plan Phase 3).
- `docs/THREAT-MODEL.md`: remove the rows this spec supersedes.
