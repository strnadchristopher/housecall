# DM-V1: end-to-end encryption for one-to-one DMs (Housecall 0.4.0)

Status: contract for implementation. Nothing here is built yet. It has been reviewed by nobody outside the project. Before W5 code starts, an Opus session reviews it as an attacker (PLAN S4); after the code is built, a fresh session attacks the running system (PLAN C6, report in `ATTACK-RUN-0.4.0.md`).

Scope: one-to-one DMs (channel `kind = "dm"`, exactly two members) only. Group DMs, channels, voice channels and calls are not end-to-end encrypted in 0.4.0 (decision A1). Device linking and QR login are in `LINK-V1.md`. `PROTOCOL.md` is a future design and does not apply.

Words "must", "must not" and "should" are used in the RFC 2119 sense. "Host" is the person running the server and everything they control: the database, every API response, and the web client's files.

Test vectors: `client/tests/vectors/dm-v1.json`, generated by `node client/scripts/security-vectors.mjs` (fixed test seeds and nonces; `--check` verifies the files on disk). That script is the reference implementation: where this text and the script disagree, the script is right and this text has a bug. Report it.

## Changes from the plan

PLAN W5 C2 and C3 were the outline. These are the places where this contract differs, and why.

1. **One 32-byte identity seed, two derived keys.** The plan had "one X25519 key and one Ed25519 key". Both are now derived from one seed (section 3). The 32-byte seed is the only secret that `key_backup` and `wrapped_keys` carry, so there is one thing to protect.
2. **The recovery key is derived from the seed and a counter, `recovery_rev`.** The plan had 256 independent random bits. With independent bits, "View recovery key" on a second device would show stale words after "Replace" on the first. Derived words can be shown on any device that holds the seed, and "Replace" is `recovery_rev + 1` (section 4).
3. **Recovery needs the words and a signed-in session.** The words open `key_backup`, which the host stores and serves only to the signed-in account. The words alone do not give someone your identity. This is stated in the explainer.
4. **The envelope goes in a new column `messages.envelope`, not in `body`.** The plan put the envelope in `body`. That would show base64 in 0.3.0 clients, notifications and any code that treats `body` as text. 0.3.0 clients now see a fixed placeholder sentence (section 14.3).
5. **The conversation key `info` is unambiguous.** The plan concatenated sorted ids and independently sorted keys. Ids are now length-prefixed and each key stays paired with its owner (section 5).
6. **The associated data names the sender and the recipient, and carries the envelope header.** Both people derive the same conversation key, so without the sender id in the associated data the host could show your message as theirs. The header puts the version byte and both key revisions under the tag (section 6).
7. **Public keys are one 65-byte versioned value, the `identity_key`.** The server still stores `agree_pub` and `sign_pub` in two columns, as the plan said.
8. **The Ed25519 key signs nothing in v1.** It is published and covered by the safety number so that a later version (signed group messages, signed device approvals) does not force every user through a key change. Nothing in v1 depends on it.
9. **The server keeps old public keys (`user_keys` table).** Without it, a peer's reset would make all earlier messages from that peer unreadable on a new device.
10. **Replacing existing keys needs the account password.** The plan let any session reset keys. A stolen session alone can no longer do that. A stolen password still can: see section 18 item 7 for what limits it.
11. **Messages that arrive under an unacknowledged changed key are held, not shown** (section 10.3). The plan only blocked sending.
12. **Pins travel with the keys when a device is linked by QR** (`LINK-V1.md` section 7), so a hostile host cannot use a newly linked device's first contact to swap a peer key.
13. **Snaps, GIFs, link previews and Apps are off in encrypted DMs. Reactions stay visible to the host.** The plan did not cover snaps, GIFs or reactions. Each is listed with its wording in section 14.
14. **Plaintext is padded to 256-byte blocks**, so the host learns message length only roughly.
15. **The server also returns 422 for `enc = 1` where encryption is not available** (group DM, or a peer without keys), so nobody can send a message the other person cannot read.
16. **Push needs no server change for the text.** Push events already carry ids only (`server/src/push.rs`). The device builds the notification text, and for `enc = 1` it uses the generic sentence (section 14.2).
17. **The web client never creates, resets or displays keys** (section 13). It can only receive them, by QR approval or recovery words, and holds them in memory.

## 1. The design in one paragraph

Each person has one identity: a 32-byte seed from which an X25519 agreement key and an Ed25519 signing key are derived. The public halves are published on every host the person uses. Two people in a DM each compute the same X25519 shared secret and derive a conversation key from it with HKDF-SHA256, bound to the channel id, both user ids and both public keys. Every message is sealed with XChaCha20-Poly1305 under that key, with a random 24-byte nonce and associated data naming the channel, sender, recipient and key revisions. Each file gets a random key, carried inside the sealed message. Clients pin the peer's public key the first time they see it and refuse to send while it is changed and not acknowledged. A recovery key (24 words) opens an encrypted copy of the seed stored on the host. There is no forward secrecy: whoever later gets either person's seed can read every message between them.

## 3. Identity

### 3.1 Notation

- `‖` concatenates byte strings. `u16be(n)` and `u32be(n)` are big-endian unsigned integers.
- `lp(s)` = `u16be(byte length of UTF-8 s) ‖ UTF-8 s`. It is used for every server id (user ids, channel ids), which are UTF-8 strings (today 64 lowercase hex characters, or `general`).
- `HKDF(ikm, salt, info, L)` = HKDF-SHA256 (RFC 5869). `salt` and `info` are bytes. Strings written in quotes are the ASCII bytes of that text with no terminator.
- `AEAD` = XChaCha20-Poly1305 (`@noble/ciphers` `xchacha20poly1305`), 32-byte key, 24-byte nonce, 16-byte tag appended to the ciphertext.
- `X25519(priv, pub)` = `x25519.getSharedSecret`. It must throw on an all-zero result (small-order peer key); `@noble/curves` 2.x does this. Callers must not catch and continue.
- `b64u` = base64url without padding (RFC 4648 section 5). Decoders must reject padding, `+`, `/`, whitespace and non-canonical trailing bits (decode, re-encode, compare).
- All randomness comes from `crypto.getRandomValues`. The vectors use fixed values so they are reproducible. A client must never use fixed values.

### 3.2 Derivation

```
seed       = 32 random bytes                                 (the identity; never leaves the device except as below)
agree_priv = HKDF(seed, salt = "housecall identity v1", info = "agree", 32)     X25519 private key
sign_seed  = HKDF(seed, salt = "housecall identity v1", info = "sign",  32)     Ed25519 secret seed (RFC 8032)
agree_pub  = x25519.getPublicKey(agree_priv)                 32 bytes
sign_pub   = ed25519.getPublicKey(sign_seed)                 32 bytes
```

The seed leaves a device only inside `key_backup` (section 4), inside `wrapped_keys` (`LINK-V1.md`), and as the recovery words (which open `key_backup`, not the seed itself).

### 3.3 Published form: `identity_key`

```
identity_key = 0x01 ‖ agree_pub (32) ‖ sign_pub (32)         65 bytes; JSON: b64u, 87 characters
```

`0x01` is the key format version. A client parsing an `identity_key` must reject: length other than 65; first byte other than `0x01`; an all-zero `agree_pub`; a `sign_pub` that is not a valid Ed25519 point encoding or is of small order. Other small-order X25519 keys are caught when `X25519` throws (vectors: "small-order peer agreement key"). The server checks the length and the version byte only (it has no curve code).

`key_rev` is a counter the **server** assigns per user: `0` means no keys; the first published key gets `1`; each different key gets the previous value plus one. Publishing the same key again does not change it. Clients never choose it; they read it and copy it into envelopes.

### 3.4 Where private keys live

The client stores exactly one identity per app install: `{ seed, recovery_rev }`. It is the same on every host the person uses (decision S-5). Private keys are derived from the seed in memory when needed.

| Platform | Storage | Rule |
|---|---|---|
| iOS | Keychain, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not synced | Same plugin as `client/src/transport/secureSession.ts` (`tauri-plugin-secure-session`), new commands `identity_get`, `identity_set`, `identity_remove`, one fixed item not keyed by origin |
| Android | Android Keystore AES-GCM wrapped file in backup-excluded storage | Same plugin, same commands |
| Desktop (Windows, macOS, Linux) | OS keyring | Same plugin, same commands. If the keyring is unavailable the app must not fall back to a file: it treats the device like the web client (memory only) and says so in Settings → Security: "This device can't store your security key safely, so you'll need your recovery key or another device each time you open Housecall." |
| Web | JavaScript memory only | Section 13 |

Never in `localStorage`, `sessionStorage`, IndexedDB, cookies, URLs, logs, crash reports, test output or the `hc-*` keys. Signing out of one host does not remove the identity (other hosts use it). "Remove this device's security key" in Settings → Security does, after a confirmation.

## 4. Recovery key and `key_backup`

### 4.1 Derivation

```
recovery_rev = 1, 2, 3, …                                     u32, starts at 1
R            = HKDF(seed, salt = "housecall recovery v1", info = "recovery key" ‖ u32be(recovery_rev), 32)
words        = BIP-39 English mnemonic of R                   24 words (@scure/bip39 entropyToMnemonic)
backup_key   = HKDF(R, salt = "housecall backup v1", info = "key backup", 32)
```

Only the BIP-39 word encoding is used, with its checksum. Nothing from BIP-32 or BIP-39 seed stretching.

### 4.2 `key_backup` format

```
key_backup = 0x01 ‖ u32be(recovery_rev) ‖ nonce (24) ‖ AEAD(backup_key, nonce, plaintext = seed (32), ad = first 5 bytes)
           = 77 bytes; JSON: b64u
```

Opening: decode; reject unless exactly 77 bytes, first byte `0x01`, `recovery_rev ≠ 0`; AEAD-open with `ad` = bytes 0 to 4; derive the identity from the seed; the derived `identity_key` must equal the account's current published `identity_key` on this host, else fail with "This recovery key belongs to a different security key." (vector "key_backup opens but belongs to another identity key").

### 4.3 Entering words

Normalise typed text: Unicode NFKD, lower case, trim, split on any whitespace, join with single spaces. Then require exactly 24 words, each in the English list, valid checksum (`mnemonicToEntropy` throws otherwise). Wording:

- Not 24 words, an unknown word, or a bad checksum: "Those words aren't a recovery key. Check each word and try again."
- Valid words that do not open the backup: "Those words don't match this account's recovery key."

The client tries the `key_backup` this host returns. There is no attempt limit on the client. The words carry 256 bits, so guessing is not a concern.

### 4.4 Showing and confirming

After creating or replacing the recovery key, the client shows the 24 words numbered 1 to 24, with "I've written them down". It then picks two different positions uniformly at random and asks for those two words ("Type word 7" and "Type word 19"). Each answer is normalised as in 4.3 and compared with the word at that position. A wrong answer says "That's not word 7. Check what you wrote." and offers "Show the words again". The client must not continue, publish keys or upload `key_backup` until both answers match (vectors `confirm_two_example` and `confirm_two_wrong`).

"View recovery key" (Settings → Security) asks for the account password first: `POST /api/me/password-check`, section 16.4. The client then fetches `key_backup`, reads its `recovery_rev`, derives `R`, checks that `R` opens it, and shows the words. If it does not open, the client shows "Your recovery key was replaced on another device. Use Replace recovery key to make a new one here." and does not show any words. The words are never copied to the clipboard automatically. A "Copy" button exists. Screenshots are not blocked.

### 4.5 Replace

"Replace recovery key": confirm with the password, `recovery_rev + 1`, show and confirm the new words (4.4), then upload a new `key_backup` to **every host this install is signed in to**. The old words stop opening the new backup. A host the install cannot reach keeps the older backup, and the old words still open that one until the install next signs in there (section 11.3 uploads the current one). Wording on the replace screen: "Your old recovery key will stop working. Anyone who already has a copy of your old words and could sign in to your account could have used them before now; if you think that happened, reset your security key instead."

## 5. Conversation key

For DM channel `C` between user `M` (me) and user `P` (peer), on one host:

```
ss   = X25519(my agree_priv, P's agree_pub)                         must not be all zero
(lo, hi) = the two parties ordered by the bytes of their UTF-8 user ids (bytewise; a proper prefix sorts first)
info = "housecall dm v1" ‖ lp(lo.user_id) ‖ lo.identity_key (65) ‖ lp(hi.user_id) ‖ hi.identity_key (65)
K    = HKDF(ss, salt = UTF-8 of C's channel id, info, 32)
```

Both sides compute the same `K`. In the vectors, alice and bob in channel `5e5e…5e` get `K = 71d057d81a36171de7eda731a8f771c7b2fa9a40ffa27dce5bb9cf1774545ca0`, and bob's id sorts first. `K` changes when either person's key changes, so each `(my key_rev, peer key_rev)` pair has its own `K`. Clients cache `K` per `(channel, my key_rev, peer key_rev)` in memory only.

A DM with the same two people on another host, or a second DM channel between them on the same host, has a different channel id and so a different key.

## 6. Message envelope

### 6.1 Payload (plaintext)

UTF-8 JSON object, at most 16384 bytes after encoding:

```json
{ "v": 1, "text": "Hello", "files": [ FileRef, … ] }
```

- `v`: must be `1`. A reader rejects any other value with "This message needs a newer version of Housecall."
- `text`: string, may be empty only when `files` is non-empty.
- `files`: optional, at most 20 entries. `FileRef` is section 7.3.
- Readers ignore unknown keys. Writers must not add keys outside this document in v1.

Replies, reactions and pins are not in the payload: they stay in the existing clear fields (`reply_to`, the reactions route, the pin route). The host sees them (section 14.4).

### 6.2 Padding

```
pad(p) = p ‖ 0x80 ‖ 0x00 × k,   k ≥ 0 the smallest value making the length a multiple of 256
```

Unpad: the length must be a non-zero multiple of 256; strip trailing `0x00`; the last remaining byte must be `0x80` and is removed; at most 256 bytes are removed in total. Anything else is rejected. 255 bytes of JSON pad to 256; 256 bytes of JSON pad to 512 (vectors).

### 6.3 Envelope and associated data

```
header   = 0x01 ‖ u32be(sender_key_rev) ‖ u32be(recipient_key_rev)          9 bytes
envelope = header ‖ nonce (24) ‖ AEAD(K, nonce, pad(payload), ad)
ad       = header ‖ lp(channel_id) ‖ lp(sender_user_id) ‖ lp(recipient_user_id)
```

- `0x01` is the envelope version. `sender_key_rev` and `recipient_key_rev` are the `key_rev` values of the two keys used to derive `K`. Neither may be 0.
- `nonce` is 24 fresh random bytes per envelope, including every edit.
- Envelope length = `33 + 256·n + 16` for `n` from 1 to 65 (the largest padded payload is 16640 bytes), so between 305 and 16689 bytes. In JSON it is b64u, at most 22252 characters.

Opening, in this order (the server runs steps 1 to 3 as well):

1. b64u-decode strictly.
2. Length is `33 + 256·n + 16` with `1 ≤ n ≤ 65`.
3. Byte 0 is `0x01`; both key revisions are non-zero.
4. Pick keys: my private key for `recipient_key_rev` (or `sender_key_rev` when I sent it), and the peer's public key for the other revision, from pins first and the server's key history otherwise (section 10.4). If my own key for that revision is gone (I reset since), show "Sent to your old security key. It can't be read on this device."
5. AEAD-open with `ad` built from the **channel id, sender id and recipient id the client already knows** for this DM (the sender is the message's `author_id`, which must be one of the two members; the recipient is the other member). A failure shows "This message couldn't be decrypted." and nothing else. Never show partial plaintext.
6. Unpad, parse JSON, check `v`.

### 6.4 Replays and duplicates

The host can store the same envelope twice under two message ids. A reader keeps, per DM, the set of nonces it has opened in loaded history, and shows a second message with a nonce already seen as a duplicate: it is hidden, and in debug builds it is logged as a duplicate with no content (vector "replayed envelope under a second server message id"). This catches replays within loaded history only. The host can still reorder, drop or delay messages, or serve an old version of an edited message (section 18).

### 6.5 Edits and deletes

An edit replaces the envelope with a new envelope (new nonce, same rules). A delete (unsend) is unchanged: the server deletes the row and its sealed files. An edit cannot change `enc` (section 15).

## 7. Attachments

### 7.1 File encryption

```
file_key = 32 random bytes per file
prefix   = 19 random bytes per file
header   = 0x01 ‖ prefix                                    20 bytes
chunk i  = plaintext bytes [65536·i, 65536·(i+1))            i = 0 … n-1, n = max(1, ceil(size / 65536))
nonce_i  = prefix ‖ u32be(i) ‖ last_i                       last_i = 0x01 for i = n-1, else 0x00
blob     = header ‖ AEAD(file_key, nonce_0, chunk 0, ad = header) ‖ … ‖ AEAD(file_key, nonce_{n-1}, chunk n-1, ad = header)
```

An empty file is one empty chunk with `last = 1` (blob = 36 bytes, vector `empty_file_blob_hex`). Decryption reads full 65552-byte pieces. Only the final piece may be shorter, it must be at least 16 bytes, and it is opened with `last = 1`. Truncation, extension or reordering fails the tag (vectors "file truncated", "file chunks reordered"). A failure shows "This file was changed after it was sent. It can't be opened." and discards everything decrypted so far.

The ciphertext size is `20 + size + 16·n`. The plaintext cap is 100 MiB (104857600 bytes), so the blob cap is `20 + 104857600 + 16·1600 = 104883220` bytes.

### 7.2 Upload

The sender encrypts the whole file on the device first, then uploads the blob through the existing upload routes with `"class": "sealed"` and `"filename": "sealed"` (section 16.5). The server stores the bytes, does not scan or transcode them, and marks the upload ready on `complete`. The sender then sends the message with `attachment_ids` and a payload whose `files` carry the keys.

The sender makes no thumbnails. A reader decrypts images to a `blob:` URL to display them, and uses `w` and `h` (when present) to reserve space so nothing shifts while it loads. Video and audio are decrypted fully before playback (no seeking into undecrypted data). They play only if the device supports the format, because sealed files are not converted.

### 7.3 `FileRef` (the attachment key wrapping)

The file key is wrapped by the message: it travels inside the sealed payload and nowhere else.

```json
{ "id": "<upload id, UUID string as the server returned it>",
  "key": "<b64u of file_key, 43 characters>",
  "name": "<original file name, 1–255 bytes UTF-8>",
  "mime": "<MIME type, e.g. image/jpeg>",
  "size": <plaintext byte length, integer>,
  "w": <optional integer pixel width>, "h": <optional integer pixel height> }
```

A reader must check that `id` is one of the message's `attachments[].id` values from the server and that the decrypted length equals `size`. On a mismatch it shows the same failure text as 7.1. It never auto-opens a file, never executes it, and shows the name and size from the `FileRef`, not from the server.

## 8. Safety number

```
(lo, hi) = the two identity_keys ordered bytewise (65 bytes each)
d        = SHA-256("housecall safety number v1" ‖ lo ‖ hi)
groups   = for g in 0..5: (big-endian integer of d[5g .. 5g+5)) mod 100000, as 5 digits with leading zeros
safety   = the six groups joined by single spaces, e.g. "16923 25721 17182 95581 09674 22368"
```

It depends only on the two public keys, not on user ids or hosts, so the same two people see the same number on every host (S-5). DM details show it with "Mark as verified". Verification is stored in the pin (section 10.1). It covers both the agreement key and the signing key. About 99.6 bits.

```sql
CREATE TABLE IF NOT EXISTS user_keys(user_id TEXT NOT NULL REFERENCES users(id), key_rev INTEGER NOT NULL,

```

Every published key is inserted here as well as into `users`, so history survives resets. For `enc = 1` rows `messages.body` is stored as the empty string.

## 10. Client rules

### 10.1 Pins

A pin is per `(host origin, peer user id)`:

```
{ identity_key: 65 bytes, key_rev: u32, verified: bool, history: { key_rev → identity_key } }
```

Pins live in the platform's secure storage next to the identity on native builds, and in memory on the web. They are not secrets, but they must not be editable by the host.

### 10.2 Key state per peer

```
          peer has no key (server key_rev 0)
NONE ─────────────────────────────────────────────► NONE      plaintext allowed, label "Not encrypted yet"
  │ server returns a valid key
  ▼  (trust on first use: pin it, verified = false)
PINNED ── server key equals pin ──────────────────► PINNED    label "End-to-end encrypted" (native)
  │ server key differs from pin, OR server says no key, OR an envelope names a peer key_rev above the pin
  ▼
CHANGED_UNACKNOWLEDGED ── user taps "I understand" ─► PINNED (new key, verified = false; old key kept in history)
```

- **No silent downgrade.** Once a peer is PINNED, the client never sends plaintext to that DM, whatever the server says. A server that reports no key for a pinned peer puts it in CHANGED_UNACKNOWLEDGED. A legitimate key is never removed (there is no route to remove one), so this only happens if the host is lying or broken. Acknowledging it does not unlock plaintext: the composer stays disabled with "christopher has no security key on this server. Messages can't be sent until they set one up again."
- **While CHANGED_UNACKNOWLEDGED:** the composer is disabled. The banner says "christopher's security key changed. This can happen if they reset their key or got a new device without their recovery key. It can also mean someone is trying to read your messages. Compare safety numbers with them before you continue." Buttons: "Compare safety numbers", "I understand". The label is "Key changed" (level 0).
- **Where changes are noticed:** on opening a DM (`GET /api/users/{id}/keys`, at most once per minute per peer), on the `keys.changed` event, and on receiving an envelope whose peer revision is above the pinned one.
- Pin on first use happens without asking. The DM details show "Not verified" until the user marks the safety number as verified.

### 10.3 Receiving under a changed key

Messages whose peer `key_rev` is above the pinned revision are not decrypted or shown while the peer is CHANGED_UNACKNOWLEDGED. The timeline shows one line: "3 messages are waiting until you check christopher's new security key." After "I understand" they are decrypted and shown normally. Messages under older revisions that are in `history` decrypt normally at any time.

### 10.4 Keys for old messages

To open an envelope the client needs the peer's key for the revision it names. It looks in the pin's `history` first. Otherwise it uses `history` from `GET /api/users/{id}/keys`. A historical key that came only from the server is trusted on first use, like any first contact, and is then added to the pin's history. A device restored from recovery words therefore trusts the server for all keys until safety numbers are compared (section 18 item 3).

### 10.5 Sending

1. The DM has exactly two members, me and the peer (from `GET /api/channels`). Anything else: do not encrypt, and do not send plaintext if the peer is pinned.
2. Fetch the peer's keys if not fetched this minute. Apply 10.2.
3. Peer NONE and the server reports `key_rev = 0`: send plaintext (`enc` omitted). The composer placeholder is "Not encrypted yet: they haven't updated".
4. Peer PINNED: seal (section 6) with my current `key_rev` and the pinned `key_rev`, and send with `enc: 1`.
5. On 422 `"this conversation is end-to-end encrypted"` (the peer just published keys): fetch keys, pin, seal, retry once. On 422 `"encryption is not available in this conversation"`: refetch keys. If the peer really has none, the server lied earlier or the peer is now keyless, and rule 10.2 applies.
6. Never put DM text into `mention_ids`, `reply_to`, typing events, link-preview requests, report bodies sent without the user choosing to report, or logs.

### 10.6 The other person has not updated

Old history stays as it was. When both people have keys, the first `enc = 1` message gets a timeline marker above it: "Messages below are end-to-end encrypted." While the peer has no key, the composer says "Not encrypted yet: they haven't updated" and the DM header shows no lock. A 0.3.0 client that receives an encrypted message shows the server's placeholder text (section 14.3). A 0.3.0 client of a person who has keys cannot send in an encrypted DM: the server returns 422 and the 0.3.0 client shows that error's text, "this conversation is end-to-end encrypted; update Housecall to send".

## 11. Key lifecycle

### 11.1 Sign-up (setup, invite accept, approved access request) on a native app

After the account exists and the three slides have been shown (PLAN C4):

1. If this install already has an identity (from another host), go to 11.3.
2. Generate `seed`, set `recovery_rev = 1`, store both in secure storage.
3. Show and confirm the recovery words (4.4). Title: "Your recovery key". Text: "These 24 words get your encrypted DMs back if you lose your devices. Write them down and keep them somewhere safe. Nobody can reset them for you, not the host and not us."
4. `PUT /api/me/keys` with the `identity_key`, then `PUT /api/me/key-backup`.

If the app is closed between steps 2 and 4, the next launch resumes at step 3 with the stored seed. Keys are published only after the words are confirmed.

### 11.2 First launch of 0.4.0 for an existing account

For each host the install is signed in to, after the session is restored:

| This install has an identity | Host has keys for this account | Action |
|---|---|---|
| no | no | 11.1 steps 2 to 4 (once for the install; later hosts use 11.3) |
| no | yes | "Get your security key" screen: "Scan a QR code from a device where you're logged in" (`LINK-V1.md` section 9, existing session) or "Enter recovery key" (4.3), or "Reset security key" (11.5) behind "I can't do either" |
| yes | no | 11.3 |
| yes, same key | yes | nothing to do; upload `key_backup` if missing or older (11.3 step 2) |
| yes, different key | yes | 11.4 |

Until this is done, the client cannot read encrypted DMs on that host. It can send only in DMs that are not encrypted (the peer has no key and is not pinned). In a DM where the peer has a key or is pinned, the composer is disabled with "Set up your security key to send encrypted messages." In the "host has keys" rows, the server refuses plaintext anyway, because both members have keys. The setup screen is offered again on every launch and from Settings → Security.

### 11.3 Joining another host with an existing identity

1. `PUT /api/me/keys` with the same `identity_key` (no password needed when the host has no key for this account).
2. `GET /api/me/key-backup`; if it is missing or its `recovery_rev` is lower than this install's, `PUT /api/me/key-backup` with a fresh seal of the current `recovery_rev`.

No new words. The same recovery key works on every host. The explainer says that two hosts can tell it is the same person (S-5).

### 11.4 Two identities collide

This install has identity X and the host has identity Y for this account (for example, another device created Y on this host before this install arrived). The client must not overwrite either silently. Screen: "This account already has a different security key on <host>." Options:

- "Get the key from your other device" or "Enter recovery key": obtain Y and make Y this install's identity. Every other host this install uses then gets Y, which is a reset there (11.5, with the password per host).
- "Use this device's key here": `PUT /api/me/keys` with X and the password. This is a reset on this host (11.5).
- "Not now".

### 11.5 Reset (keys lost, or a stolen device)

Settings → Security → "Reset security key", or "I can't do either" on the setup screen. Confirmation screen, exact text:

> **Reset your security key?**
> Your encrypted messages from before the reset can't be read on any device after this, unless one of your devices still has the old key. Everyone you have an encrypted DM with will see that your security key changed and will need to accept it before they can send to you. Use this if you lost your devices and your recovery key, or if a device with your key was stolen.

Buttons: "Reset security key" (destructive style) and "Cancel". Then the password, a new seed with `recovery_rev = 1`, words confirmed (4.4), `PUT /api/me/keys` with the password, `PUT /api/me/key-backup`, and the same on every other host this install is signed in to.

What others see: the server increments `key_rev`, keeps the old key in `user_keys`, clears `key_backup`, and emits `keys.changed`. Each DM peer's client moves to CHANGED_UNACKNOWLEDGED (10.2). The user's other devices that still hold the old seed show "Your security key was replaced on <device name>. If this wasn't you, change your password and reset your key again." They stop sending (their key no longer matches) until they get the new key by QR or recovery words. The device name comes from the session that made the change, carried in the event.

### 11.6 `key_rev` summary

- 0: no keys. Never goes back to 0.
- First `PUT /api/me/keys`: 1.
- Same key again: unchanged, 200.
- Different key (reset, collision fix): +1, needs the password, needs the account to already have keys.
- Envelopes carry the revisions used. `user_keys` keeps every revision.

## 12. Multi-device

All devices of a person hold the same seed. A device gets it in exactly two ways:

1. **QR approval** from a device that has it (`LINK-V1.md`). This also copies that device's pins and verifications.
2. **Typing the recovery words** on a device signed in to a host that has the account's `key_backup` (4.3). No pins come with it: every peer is trust on first use again on that device, and DM details show "Not verified on this device".

There is no third way. A device never generates a second identity for an account that already has one, except through reset (11.5) or the collision choice (11.4).

## 13. The web client (assumption A3)

- The web client may hold the seed **in memory only**, after QR approval or recovery words in the current page session. Reloading or closing the tab forgets it. It is never written to any browser storage.
- The web client must not create an identity, reset it, replace the recovery key, show the recovery words, or act as the approving device in `LINK-V1.md`. Those screens say "Use the Housecall app on your phone or computer for this."
- A web user without keys in memory sees encrypted DMs as "Locked in this browser. Scan a QR code or enter your recovery key to read them." and cannot send to pinned peers.
- Label in the web client, even with keys: "Encrypted in browser" (never "End-to-end encrypted"). Detail: "This browser loads its app from the host, so the host could change it and read this conversation. Use the Housecall app for end-to-end encryption."
- Pins in the web client are memory only and start empty each session (trust on first use every time). This is part of why the web label is weaker.

## 15. Server rules

### 15.1 Encrypted DM

A channel is an **encrypted DM** when `kind = 'dm'`, it has exactly two members, and both have `key_rev > 0`. This is computed at request time; nothing is cached.

### 15.2 Send and edit

`POST /api/channels/{id}/messages` and `PATCH /api/messages/{id}`:

| Request | Encrypted DM | Any other conversation |
|---|---|---|
| `enc` absent or 0 | **422** `this conversation is end-to-end encrypted; update Housecall to send` | Accepted as today |
| `enc: 1` | Validate (below), store | **422** `encryption is not available in this conversation` |

Validation for `enc: 1`, all must hold or **422** `invalid encrypted message`:

- `envelope` is a string of at most 22252 characters, strict b64u. The decoded length is `33 + 256·n + 16` with `1 ≤ n ≤ 65`, byte 0 is `0x01`, and both key revisions are non-zero.
- The envelope's sender revision equals the author's current `key_rev`, and its recipient revision equals the other member's current `key_rev`. Otherwise **409** `security key changed; reload keys`. This stops a client sending under a key the server already knows is stale. It is not a security check: the client never relies on it.
- `body` is absent or empty. `view_once` is false. `role_mention_ids` is empty. `mention_ids` is empty or contains only the other member (notification routing).
- Each `attachment_ids` entry is a `sealed` upload by this author for this channel, ready, not attached elsewhere. With `enc` 0, sealed uploads are refused (**400** `attachment must be clean and in this conversation`).
- Edit: the stored row's `enc` must equal the request's. Changing it gives **422** `invalid encrypted message`.

The server never decrypts, never parses beyond the header, and never logs `envelope`.

### 15.3 Read

Message JSON gains `"enc": 0|1` and `"envelope": string|null`. For `enc = 1`, `body` is the placeholder (14.3). Attachments of sealed uploads have `"kind": "sealed"`, `"filename": "sealed"` and no `video_path` or `thumbnail_path`.

### 15.4 Keys

- `PUT /api/me/keys`: `identity_key` must decode (strict b64u) to 65 bytes starting with `0x01` and an `agree_pub` that is not all zero, else **400** `invalid identity key`. Same as the current key: 200, unchanged. No current key: store, `key_rev = 1`. Different key: requires `password` (Argon2 verify through the existing `auth_slots` semaphore). A wrong or missing password gives **403** `password required`. Then store, `key_rev + 1`, `key_backup = NULL`. Every accepted change inserts into `user_keys` and emits `keys.changed` (15.6).
- Disabled users: 404 on reads, as elsewhere.
- No route deletes keys.

### 15.5 Key backup

`PUT /api/me/key-backup`: the account must have keys (else **409** `publish keys first`). The value must decode to exactly 77 bytes with byte 0 `0x01` and `recovery_rev ≥ 1` (else **400** `invalid key backup`). Its `recovery_rev` must be ≥ the stored one (else **409** `a newer recovery key exists`). Equal is accepted (a re-seal). `GET` returns it to the account itself only.

### 15.6 Events

- `keys.changed` `{ "user_id", "key_rev", "device_name" }`: to the user's own sessions and to every user who shares a `dm` channel with them. `device_name` is the changing session's name.
- `key_backup.changed` is not emitted. Clients check on "View recovery key".

### 15.7 Rate limits (the existing per-minute `limited()` buckets)

| Route | Limit |
|---|---|
| `PUT /api/me/keys` | 3 per minute per user |
| `PUT /api/me/key-backup` | 6 per minute per user |
| `POST /api/me/password-check` | 5 per minute per user, plus `auth_slots` |
| `GET /api/users/{id}/keys`, `GET /api/me/key-backup` | the session's general 600 per minute |

### 15.8 Logging

Never log: `envelope`, `identity_key` bytes, `key_backup`, passwords, or request bodies of these routes. Log at info: `keys published user=<id> key_rev=<n>`, `keys replaced user=<id> key_rev=<n> session=<session id>`, `key backup stored user=<id> recovery_rev=<n>`, and 422 refusals with user and channel ids only.

### 15.9 Push (PLAN C5)

Push events carry message and channel ids only (unchanged). The device builds notification text locally. For `enc = 1` it uses "New message from <name>" and does not decrypt in the notification extension in v1. CallKit is unchanged. Test: an `enc = 1` message to a member with a push device produces a push event, and the payload contains no envelope or body.

## 16. API

All routes are under `/api`. Private routes need the existing `Authorization: Bearer` and `X-Device-Key` headers. Error bodies are `{"error": "<text>"}` as elsewhere. Binary values are b64u strings.

### 16.1 `PUT /api/me/keys`

```json
{ "identity_key": "AbH5jbiGvuvaHV3kG_6oZEcMoJ3Az7nyG1EVfp3iztwbAvgNSBLgTvFUlXIMURiJe_0OM7rlejJXE4AvmTl6XFE",
  "password": "only when replacing an existing key" }
```
→ 200 `{ "key_rev": 1 }`. Errors: 400 `invalid identity key`, 403 `password required`, 429.

### 16.2 `GET /api/users/{id}/keys`

Any signed-in user may read any enabled user's keys (the member list is already visible to all).

```json
{ "user_id": "0f1e2d3c4b5a69788796a5b4c3d2e1f00f1e2d3c4b5a69788796a5b4c3d2e1f0",
  "identity_key": "<b64u, 87 characters: current key>", "key_rev": 2,
  "history": [ { "key_rev": 1, "identity_key": "<b64u, 87 characters>", "created_at": 1763000000000 },
               { "key_rev": 2, "identity_key": "<b64u, 87 characters: same as current>", "created_at": 1763100000000 } ] }
```
With no keys: `{ "user_id": "…", "identity_key": null, "key_rev": 0, "history": [] }`. Unknown or disabled user: 404.

### 16.3 `PUT /api/me/key-backup` and `GET /api/me/key-backup`

PUT body `{ "key_backup": "<b64u, 103 characters>" }` → 200 `{ "recovery_rev": 1 }`.
GET → 200 `{ "key_backup": "<b64u>" }` or `{ "key_backup": null }`.

### 16.4 `POST /api/me/password-check`

`{ "password": "…" }` → 200 `{ "ok": true }` or 403 `password required`. Used before "View recovery key" and "Replace recovery key". It makes no state change.

### 16.5 Uploads

`POST /api/uploads` gains an optional `"class": "sealed"`. For `sealed`:

- The channel must be an encrypted DM the caller is in (else **422** `encryption is not available in this conversation`).
- `filename` must be `sealed`, else 400.
- `length` must be at most 104883220, else **413**.
- `complete` marks the upload ready **without scanning**. Transcode jobs are never created for it.
- `GET /api/media/{id}` serves the bytes as `application/octet-stream` with `Content-Disposition: attachment`.

Today's per-chunk `PATCH` and resume behaviour is unchanged.

### 16.6 Messages

Send: `{ "enc": 1, "envelope": "<b64u>", "attachment_ids": ["<uuid>"], "reply_to": "<id or null>", "mention_ids": ["<peer id>"] }`.
Edit: `{ "enc": 1, "envelope": "<b64u>", "revision": 3 }`.
Read: message objects gain `enc` and `envelope` (15.3).

### 16.7 Members

`GET /api/members` entries gain `"key_rev": <int>`, so a client knows who has keys without one request per person. `GET /api/me` `user` gains `"key_rev"`.

### 16.8 Route inventory

All routes above are private. None goes in the `public` set of `server/tests/route_inventory.rs`.

## 18. Known limits (stated plainly)

1. **No forward secrecy.** Whoever later gets either person's seed (a stolen unlocked device, recovery words together with account access, malware) can read every encrypted message between them, past and future, until both reset.
2. **Metadata is visible to the host:** who talks to whom, when, how often, sizes to 256 bytes, file sizes, reactions, reply structure, pins, read and typing state, device names, IP addresses.
3. **Trust on first use.** The first time a device sees a peer's key (and on any device restored from recovery words, and in every web session) the host can substitute its own key. Only comparing safety numbers detects it.
4. **Calls are relayed and not end-to-end encrypted**, including DM calls. The host could listen.
5. **No outside audit.** The design and code are reviewed and attack-tested by models working for the project, not by an independent firm.
6. **The same identity on several hosts is linkable.** Two hosts that compare `identity_key` values can tell it is the same person.
7. **A password thief can reset your keys.** They cannot read old messages, but after a reset, peers who tap "I understand" without checking will send to the thief's key. Every peer sees the change, and every device that still has the old key raises an alarm.
8. **The host can drop, delay, reorder or replay messages and roll back edits.** Clients catch replays only within loaded history. There is no sequence numbering in v1.
9. **The web client is only as trustworthy as the host** that serves it.
10. **Either person can fake a message "from" the other on their own screen.** Both hold the same key, so encrypted messages prove nothing to a third party. This is intended: there is no non-repudiation.
11. **A replay across hosts:** a host that controls two servers where the same two people have DMs, and copies channel and user ids, can replay a genuine message from one into the other.
12. **Deleting is not erasure.** The other person's device, backups and the host's disk may keep ciphertext. The host cannot read it, but anyone who later gets a seed can.
13. **The recovery words are the spare key.** Anyone with the words and access to the account can take the identity.

## 19. Attack-run checklist (input to PLAN C6)

Each must fail against the built system. The report says how it was tried.

- Read a DM from the SQLite file.
- Change `author_id` on an encrypted row and see whether the client shows the wrong sender (it must fail to decrypt).
- Swap a peer key in `users` and `user_keys` (pinned client: "Key changed"; held messages not shown).
- Set a peer's keys to NULL (pinned client: composer disabled, no plaintext sent).
- Send `enc` 0 in an encrypted DM (422). Send `enc` 1 in a group DM (422).
- Replay an envelope as a new row (shown once).
- Truncate, extend or bit-flip an envelope or a sealed file (refused).
- Open `key_backup` without the words.
- Reset keys with a stolen session and no password (403).
- Make the web client persist the seed anywhere.
- Get any plaintext into server logs, push payloads, preview fetches or reports without the user choosing to report.
