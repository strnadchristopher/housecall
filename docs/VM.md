# Shared VM implementation boundary

Rabb.it used a shared remotely hosted browser: all viewers saw the same browsing session and control could change hands. This differs from independently playing a movie at synchronized timestamps. Background: [Rabb.it](https://en.wikipedia.org/wiki/Rabb.it).

The optional compose VM profile launches QEMU/KVM with an administrator-prepared Debian base disk, persistent qcow2 overlay, Unix-socket QMP and VNC, and no TCP control listeners. It joins the **existing** Gluetun container network namespace; no fallback network exists. It refuses startup without tun0/wg0. See [Gluetun namespace guidance](https://github.com/qdm12/gluetun-wiki/blob/main/setup/connect-a-container-to-gluetun.md) and [firewall](https://github.com/qdm12/gluetun-wiki/blob/main/faq/firewall.md). The startup check does not prove the runtime kill-switch. A Gluetun configuration that allows LAN destinations also allows the guest to reach them; avoid outbound subnet exceptions for this activity.

NOT COMPLETE: Debian image provisioning, authenticated WebRTC capture/audio bridge, integrating the controller lease with QMP, snapshot reset API, guest-to-LAN isolation, and a live VPN kill-switch test. VNC/QMP are internal transport plumbing, not the required WebRTC user experience. Do not expose these sockets through an unauthenticated proxy. Do not start this profile on Shiva as part of development.

Acceptance must test from **inside the guest**, not only the container: record public exit IP with VPN healthy; remove tunnel and verify IPv4, IPv6 and DNS all fail; restore and verify recovery; stop Gluetun and verify guest cannot reconnect via default Docker network. Use an isolated disposable local VPN fixture, never stop the existing production Gluetun container. Test revocation/controller handoff while input events are queued. Reset only after all participants are notified and the owner confirms the exact session reset; stop QEMU, atomically replace the overlay, restart, and verify base checksum unchanged.
