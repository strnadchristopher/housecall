# Media compatibility and security — proposal

**Not approved or implemented. No runtime, quarantine, scanner selection, or release default changes are authorized by this document.** The project requires intense upload security **and no upload size cap except available disk**. A paid scanner was not a requirement. Preserve the optional WithSecure adapter and its qualification work; purchasing, installing, or qualifying it is not a prerequisite for choosing the no-new-spending approach below. The maintainers must review the policy and implementation scope before any behavior changes.

## Recommendation and current boundary

Keep encrypted, immutable originals as untrusted data; represent scanner coverage separately from upload completion and playback availability. Recommend a reviewed, explicit download action for coverage-limited originals, never automatic inline rendering. For supported media, generate separate, constrained playback objects in an isolated worker and scan each complete output before publication. This reduces exposure; it cannot guarantee an original or derivative contains no unknown exploit.

Current code is stricter: `crates/media/src/lib.rs` `Store::finalize` quarantines before scanning, accepts only scanner success with all source bytes consumed, and `read_range` requires `Ready`. `server/src/transcode.rs` `start` also requires `Ready`; `run_job` derives one MP4 and thumbnail, then scans both before publishing. The scanner trait currently returns only success/error; ClamAV errors and detections collapse to quarantine/HTTP 423. A 423 is not evidence of positive malware detection.

`server/src/media.rs` already sends originals as `application/octet-stream` with `Content-Disposition: attachment`; global middleware supplies `nosniff` and `no-store`. Derivative routes intentionally override MIME/disposition for playback. Preserve these authorization and response boundaries. The proposed unknown-download and unknown-source worker access require separate reviewed capabilities, **not** making `read_range` accept quarantine or treating unknown as `Ready`.

## Proposed decision table

These actions describe the proposed policy **after approval and verified implementation**, not current capabilities. Source and derivative verdicts remain independent; a successful conversion never clears the source.

| Evidence/status | Original action | Playback and recovery |
| --- | --- | --- |
| Detected malware or other explicit blocking security verdict | Block all recipient/owner downloads; retain encrypted quarantine for deletion or controlled rescan. No “download anyway.” | Block/cancel source jobs and withdraw derived access. False positives require reviewed rescan, never a user bypass. |
| Whole object scanned, no finding, supported analysis completed under recorded policy | Authenticated attachment download; label “Scanned — no threats found,” not “safe.” | Supported media may process; inline playback only after separate output validation/scans. |
| Coverage limited: oversized, unsupported, encrypted content, archive depth/expansion limit, incomplete parser coverage | Keep status “Scan incomplete” and reason. Recommend explicit “Download original — scan incomplete” only under the reviewed policy and affirmative per-file user action. | Supported media may enter the isolated worker; archives/nonmedia receive no media preview. Published outputs need their own complete scans. Retry scan if coverage changes. |
| Scanner unavailable, stale under configured freshness policy, timeout, transport/parse error, ambiguous reply | “Scan unavailable/failed”; block downloads pending retry. Never downgrade an error into the coverage-limited download path. | No new output release. Queue bounded retry or offer retry after recovery; do not silently use a different engine. |
| Decoding failed, unsupported codec/container, integrity error or processing budget exceeded | Preserve independent source scan status; integrity failure blocks reads, otherwise original action follows its scan row. | No partial success. Remove unpublished outputs; show reason and retryability. A processing failure is not a malware verdict or permanent upload-size limit. |

Detected takes precedence over every other state, including a later scanner outage. Existing ambiguous quarantines remain blocked until classified through fresh evidence; migration must not infer “oversized” solely from length. Incomplete uploads cannot be downloaded. Report attachments retain their stricter owner-only authorization.

## What scanning establishes

The checked-in ClamAV configuration uses `StreamMaxLength 2048M`, `MaxFileSize 2048M`, `MaxScanSize 4096M` and `AlertExceedsMax yes`. Upstream still documents an approximately 2 GiB single-file analyzer ceiling. Raising stream admission or scanning arbitrary chunks does not remove that ceiling or reconstruct archive/container analysis. Keep limit alerts enabled; classify a recognized limit alert as coverage-limited, not as proven malware or no-finding. ClamAV also documents archive recursion, encrypted-content alerts and additional analysis limits. An `OK` response alone cannot establish supported full analysis for every file type. Record engine/signature versions, policy, object identity, completion and known coverage restrictions. [ClamAV official configuration](https://raw.githubusercontent.com/Cisco-Talos/clamav/main/etc/clamd.conf.sample), [upstream size-limit explanation](https://blog.clamav.net/2023/08/clamav-120-release-candidate-now.html).

Archive/encrypted/nonmedia uploads remain valid encrypted storage objects without a total size cap. Do not extract them in the API, decrypt user archives using uploaded passwords, launch executable content, or send them to external analysis. Supported archive scanning needs bounded recursive/expanded-byte accounting; encryption, unsupported members and exhausted limits mean unknown coverage. MIME sniffing, file extensions, successful decoding and signature absence are not interchangeable security verdicts. Unknown exploits and scanner parser vulnerabilities remain residual risks.

## Worker and output requirements

This is an implementation proposal, not a claim about the existing FFmpeg subprocess. Current `derive_one` already clears environment, uses fixed arguments, `pipe` protocol allowlisting, one thread, bounded probes/single allocations and an outer timeout. It still runs under the API's identity; those options do not establish service isolation or a total memory bound.

- Use a separate unprivileged worker with no media key, database, host home, service credentials, Docker socket, arbitrary mounts or network access. Feed only one authorized immutable source through scoped descriptors/broker access; return outputs through bounded channels. Use a read-only root, private scratch, dropped capabilities, no-new-privileges, isolated namespaces and a tested seccomp syscall/architecture allowlist. Fail startup if required isolation is ineffective. Scanner services need equivalent containment; signature updates use a separate narrowly permitted updater. Linux systemd or container controls can implement these boundaries, but their effective behavior must be tested on the target host. [systemd isolation and syscall controls](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html).
- Preserve FFmpeg protocol allowlisting and fixed format/codec selection; disable unnecessary protocols/demuxers where feasible. A pipe-only input avoids URL protocols but cannot itself stop compromised decoder code from using syscalls. Some legitimate containers need seeking: support scoped random access to authenticated decrypted ranges, or explicitly show processing unsupported while retaining the original; never silently spool the entire plaintext source to host `/tmp`. [FFmpeg protocols](https://ffmpeg.org/ffmpeg-protocols.html).
- Initial review budget: one active decoder, at most two CPU cores, 2 GiB cgroup memory, 64 processes, 128 descriptors, 256 MiB private tmpfs, 6-hour wall deadline and 120-second no-progress deadline. Bound the scanner separately (candidate 4 GiB memory, one scan at a time); measure the combined host budget before adopting these numbers. Kill/reap the entire owned worker group/cgroup on timeout, cancellation or source revocation. Reserve and meter actual scratch/output disk use, including scanner expansion; fail recoverably before exhausting the host. These are processing budgets, never maximum accepted original lengths. Long inputs need resumable processing/checkpoints or explicit retry under a reviewed larger budget.
- Encrypt persisted originals, intermediates and derivatives. Use memory-only bounded scratch, or encrypted spill with per-job access and cleanup; no plaintext caches, core dumps or logs. Tmpfs can swap: prohibit swap for all plaintext-handling processes/mounts with verified host controls, or use encrypted swap and encrypted hibernation storage under an explicit host policy. `PrivateTmp` or a tmpfs mount alone is insufficient. Include scanner temporary storage and decrypted API buffers in this assessment. [Linux tmpfs behavior](https://www.kernel.org/doc/html/latest/filesystems/tmpfs.html).
- Decode/re-encode only approved audio/video streams; strip attachments, scripts, data tracks and unneeded metadata. Generate independently scannable complete output objects, initially targeting ≤32 MiB each, comfortably below the **effective** analyzer limits. Re-encode/resegment if an object exceeds that budget; do not truncate or reject the original. Each object needs EOF, integrity, format/codec validation and a complete no-finding scan before exposure. Never claim arbitrary source chunk scans or an isolated fragment without required container context proves coverage. For fragmented formats, qualification must include the required initialization context and exact served bytes.
- Publish an authenticated server-generated index only after the required output set passes; use server-owned IDs, bounded timestamps/counts, no external URLs or user manifests. Every referenced initialization object, segment and thumbnail needs a verified receipt. All ranges and index/segment requests enforce current membership and source lifecycle. Decoder success alone does not grant publication. Cancellation, restart, a late detection or deletion must prevent stale output commits. Sandboxing and transcoding reduce risk; kernel/decoder escapes and downstream playback bugs remain possible.

## Compatibility and migration

Add versioned scan/coverage records and independent processing status before enabling new actions. Expose only sanitized reason codes, engine/policy freshness and permitted actions to clients; keep raw diagnostics private. Preserve existing status contracts conservatively: old clients must never see unknown originals as `ready`. Existing `Ready` records without coverage receipts remain legacy scan evidence, not retroactively certified; revalidate before assigning the new full-coverage label. Keep the current strict mode available for rollback and preserve encrypted data when rolling back.

Separate “upload finished,” “scan incomplete,” “processing,” “playback available” and “download original” in the functional contract. Downloads require active device/session and membership checks, safe attachment MIME/disposition, `nosniff`, `no-store`, and no automatic opening or public bearer URLs. Byte-range requests must not bypass the explicit unknown-download action. These headers reduce browser execution exposure; they do not protect a recipient who opens the downloaded file locally. Opus owns presentation/interaction design; this proposal specifies truthful state/action boundaries only.

Segmented playback needs an authenticated seek/index transport and desktop/mobile compatibility work. Preserve the existing MP4 route for qualified small media until clients support the new contract. No inference of Safari/iOS or Tauri WebView support from desktop browser success. WithSecure remains an optional separately selected experiment; its own license/privacy/large-object qualification applies only if that path is chosen. A vendor size claim is not a universal AV guarantee.

## Acceptance evidence required before changing the default

Use assistant-authored data in isolated fixtures when the host execution lane is available; this document runs nothing. Record exact source/artifact hashes, engine/signature/policy versions, budgets, outcomes and cleanup receipts.

1. **Usable large media:** actual >2 GiB video payload, not padding/sparse bytes; interrupt upload and restart/resume from the durable offset, compare authenticated beginning/end ranges with source hashes, derive playable output, seek early/middle/late and outside buffered ranges, and verify audio/video duration and continuity on browser and supported native clients. Original must stay coverage-limited under ClamAV; separately scanned derivatives can become available only under the approved policy.
2. **Truthful security states:** harmless EICAR controls and supported archive variants establish positive detection separately from limit rejection; encrypted/nested/unsupported and >2 GiB inputs retain explicit coverage limitations. Scanner outage, stale definitions, malformed reply, partial read and timeout never yield no-finding or actionable unknown download. Under reviewed unknown-download policy, verify explicit consent, attachment headers and no inline preview. All detected cases remain blocked.
3. **Containment and output:** bounded fixture attempts to access host files/network fail from inside the real worker; effective memory/CPU/process/scratch/swap limits are recorded. Inject output scan failure in the last segment and verify no index or partial output set becomes available. Check malformed media, archive expansion and output-budget exhaustion fail safely; no plaintext spill or surviving child after cleanup. This verifies controls, not absence of every sandbox escape.
4. **Recovery and authorization:** disk-full leaves upload offset durable and recoverable; worker crash/restart and scanner recovery allow retry without reupload. Delete/unsend/revoke during scanning, processing and playback; verify original/index/all segment ranges deny unauthorized access and stale jobs cannot republish. Retry after a processing-budget failure must not reclassify the original as permanently too large.

Retained evidence is narrower: `evidence/client-multigib.json` proves 2,147,483,771-byte browser resume followed by quarantine; `evidence/media-multigib.log` uses a fixture scanner and disclaims malware coverage. `evidence/client-upload-video.json` proves real scanner/FFmpeg playback of a 60-second source but explicitly leaves outside-buffer seeking and native WebViews unverified. `evidence/recovery-scanner-source-review.md` is source review only. The optional whole-object engine harness is authored but unexecuted. None establishes this proposed default or satisfies the combined large-video outcome.

**Decision for maintainers:** approve/revise the unknown-original action and isolated unknown-source processing boundary, then approve the staged compatibility/containment implementation and its acceptance evidence. Until then, preserve current quarantine and release gates. No scanner purchase or new spending is requested.
